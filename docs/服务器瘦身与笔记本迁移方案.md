# 服务器瘦身 + 笔记本接管：迁移方案

> 目标：把业务从当前这台 **2 vCPU / 1.6G 内存** 的阿里云 ECS 搬到家中的
> **16 核 / 16G、走 WiFi** 笔记本上，服务器只保留「必须暴露在公网」的部分。
>
> 文档基于 2026-10-03 对现网的实际体检数据，不是通用模板。

---

## 0. 结论速览（TL;DR）

| 项 | 结论 |
|---|---|
| **笔记本系统** | **Ubuntu Server 24.04 LTS**（与现服务器同版本）。不要选 Windows。 |
| **服务器保留** | nginx(80/443 + TLS) · SSH · WireGuard 服务端 · （可选）MC 25565 四层转发 |
| **笔记本承担** | Minecraft 服务端 + MC bot + AI 栈(dsh / qq-bridge / SnowLuma) + AniHub + 推流 + 代理 |
| **核心难点** | 不是算力，是**网络**：笔记本走 WiFi 在 NAT 后面，没有公网 IP（第 5 节） |
| **最大收益** | 内存从「靠 3.5G swap 续命」变成富余 3~7G；MC 堆从 384M 提到 4~6G；服务器磁盘从 92% 降下来 |

**判断：这台机器已经在靠 swap 活着。** load 5.1 在 2 核上意味着平均有 3 个以上进程在排队；

## 2. 瓶颈定位：谁该走

搬家的正确顺序 = 按「吃资源 / 与硬件耦合 / 是否依赖公网 IP」排序：

1. **Minecraft 全家桶**（Java + botd + 推流）—— CPU 最大头（24%+6%），且**天然该在算力富余的机器上**；世界文件大，磁盘也占。
2. **AI 栈**（dsh + qq-bridge + embedder + SnowLuma/QQ）—— 内存最大头（159+114+74+34 ≈ **380M，占全机 1/4**），且它们互相依赖 localhost，必须整体搬。
3. **AniHub** —— 纯 Node 站点，搬走只是改个 `proxy_pass`。
4. **Clash 代理 + Xvfb/VNC 四件套** —— 为了给 pixiv/B站取图做代理；qq-bridge 一走，代理也该跟着走。
5. **nginx + TLS** —— **留在服务器**，这是真正的「必要公网行为」。
6. **quanti** —— 当前没跑；一起搬还是删掉，见第 11 节。

### 3.1 留 / 走 对照表

| 组件 | 去向 | 理由 |
|---|---|---|
| nginx + Let's Encrypt | **留服务器** | 唯一需要 80/443 的入口；证书续期不动 |
| sshd | **留服务器** | 唯一带外公网 IP 的登录点 |
| WireGuard | **留服务器**（服务端） | 隧道锚点 |
| nftables DNAT 25565 | **留服务器**（条件性） | 见 5.2，家里能端口映射就不需要 |
| Minecraft 服务端 | ➡️ 笔记本 | 吃 CPU，世界文件大 |
| botd + milestone runner | ➡️ 笔记本 | 与 MC 同机才低延迟（走 localhost 而非隧道） |
| ffmpeg 推流 | ➡️ 笔记本 | **必须直连 B站**，不要经服务器吃带宽 |
| DSH Harness | ➡️ 笔记本 | 与 qq-bridge 通过 127.0.0.1:3080 耦合 |
| qq-bridge + embedder | ➡️ 笔记本 | 同上 |
| SnowLuma + QQ NT (docker) | ➡️ 笔记本 | 与 qq-bridge 通过 127.0.0.1 耦合 |
| AniHub | ➡️ 笔记本 | 由服务器 nginx 反代隧道过去 |
| Clash Verge + mihomo | ➡️ 笔记本 | 使用者（qq-bridge）搬了 |
| Xvfb / x11vnc / noVNC | ➡️ 笔记本（降级为按需） | 只在需要扫码/人工介入时开 |
| certbot | **留服务器** | 跟着 nginx |
| 云监控 agent | **留服务器** | 阿里云合规要求 |

> ⚠️ **一个容易被忽略的点**：你现在是通过 `127.0.0.1:3080` 上的 DSH Web GUI 在跟我对话。
> DSH 搬到笔记本后，这个 GUI 也跟着走。访问方式要么走 WireGuard（`http://10.77.0.2:3080`），
> 要么 `ssh -L 3080:127.0.0.1:3080 wx@笔记本` 端口转发 —— **不要**把 3080 暴露到公网。

## 4. 系统选型：Windows 还是 Linux

### 4.1 结论

> ## 选 **Linux**，具体用 **Ubuntu Server 24.04 LTS**。

不是出于偏好，而是因为这套业务的每一层都已经长在 Linux 上了：

1. **迁移 = 复制目录 + 复制 unit 文件 + 改路径。**
   现网所有编排都是 Linux 原生的：5 个自定义 systemd 单元、Docker 容器、`mc.sh` / `bot.sh` /
   `stream.sh` / `start.sh` 四套 bash 脚本。换 Windows 意味着把这些**全部重写**成
   NSSM/计划任务 + `.bat`/PowerShell，而且改动本身就是新 bug 的来源。

2. **QQ NT 这条链是 Linux 专用的。**
   现在是 `motricseven7/snowluma` **Linux 镜像**里的 QQ + Xvfb + x11vnc + noVNC 四层栈。
   这台机器上只有 `SnowLuma-v1.14.17-linux-x64`，没有 Windows 发行版。
   换 Windows 虽然能用原生 QQ（这是 Windows 唯一的真优势），但要换一整套 SnowLuma 发行版，
   属于「把能跑的东西推到没验证过的路径上」。

3. **7×24 无人值守，Linux 是碾压性的。**
   Windows Update 会在凌晨重启、驱动更新会重启、GUI 程序（QQ）要求有交互式登录会话
   （不配自动登录+计划任务就起不来）。Linux 上 systemd 开机自启 + `Restart=always`
   就是全部所需，SSH 管理，没有意外重启。

4. **16G 内存要省着给 MC。**
   Windows 11 空载吃 3~4G；Ubuntu Server 空载 ~500M。差的这 3G 正好是 MC 堆从 384M
   提到 4G 的本钱。用 Docker Desktop 还要再送一个 WSL2 VM（2~4G）+ 商用授权问题。

5. **Docker 原生。**
   SnowLuma 是容器，Linux 上 docker 直跑；Windows 上 Docker Desktop 是虚拟机，多一层开销与故障面。

### 4.2 对比表

| 维度 | Ubuntu Server 24.04 | Windows 11 Pro |
|---|---|---|
| 迁移工作量 | **极低**：改路径即可 | 高：服务化、脚本、路径全重写 |
| QQ NT / SnowLuma | **现成镜像，已验证** | 需换 Windows 发行版，未验证 |
| 开机自启 / 守护 | systemd，一行配置 | NSSM / 计划任务 / winSW |
| 意外重启风险 | 低（可控内核更新） | **高**（Windows Update 强制） |
| 空载内存占用 | ~500 MB | 3~4 GB |
| 无显示器运行 | **原生**（SSH） | 需 RDP；GUI 程序要求登录会话 |
| Docker | 原生 | Desktop = VM + 授权 |
| 远程管理 | SSH | RDP（重、慢） |
| 无线网卡兼容性 | 需先验证（**唯一风险点**） | **最好** |
| 硬件编码 (NVENC/QSV) | 支持，配置略繁 | 生态更顺 |
| 人工介入（扫码/人脸） | 靠 noVNC（现已有） | 本地桌面最方便 |

### 4.3 什么情况下才该选 Windows

只有一种：**这台笔记本同时还是你日常办公/游戏的主力机**，必须留着 Windows。
那种情况下我的建议不是「装 Windows 当服务器」，而是：

- 方案 A（推荐）：**双系统** —— Windows 日常用，Ubuntu 分区专门做服务器（开机默认进 Ubuntu）。
- 方案 B：Windows + WSL2 跑 Linux 侧业务 —— 能跑，但 Docker Desktop + WSL2 的内存开销和
  「Windows 一重启全停」的问题都在，属于将就。

**如果笔记本是纯服务器（哪怕偶尔接显示器），就装 Ubuntu Server，不要犹豫。**

### 4.4 安装建议

- 版本：**Ubuntu Server 24.04 LTS**（与现服务器同版本，命令、包名、systemd 行为完全一致）
- 备选：Debian 12（更精简，但现网是 Ubuntu，没必要引入差异）
- 桌面环境：**基底不装，需要时按需再加** —— 见 4.5
- 进阶可选：**Proxmox VE**（Debian 底），把每个业务放进独立 LXC/VM，好处是**快照回滚**。
  代价是多一层学习成本。第 7 节的迁移步骤按「裸机 Ubuntu + Docker + systemd」写，
  用 Proxmox 的话把每步的「目录」换成「LXC 容器」即可。
- 分区：`/` 至少 200G；数据（MC 世界、docker 卷、anihub）可以单独挂一个区方便备份

### 4.5 图形界面：要还是不要

**结论：基底装 Server，图形按需再加。这不是二选一，而且反悔成本不对称** ——
Server 上加桌面是一条 `apt install`，桌面卸回 Server 会很脏。**所以先 Server，缺了再加。**

#### 这套业务里，哪些环节真的需要图形？

| 需要人工介入的环节 | 现在的做法 | 装了桌面有帮助吗 |
|---|---|---|
| QQ 扫码登录 / 滑块验证 | noVNC 看容器内的 Xvfb（:6082） | ❌ 没帮助 —— QQ 跑在容器里，还是得开 noVNC |
| B站扫码登录 | `bili-qr-serve.js` 用 HTTP 出二维码 | ❌ 不需要 |
| B站推流人脸核验(60043) | **手机 App** | ❌ 只能在手机上做 |
| Clash Verge 调节点 | noVNC 看 Xvfb（:99）的 GUI | ⚠️ 有点用，但 mihomo 也有命令行/Web 面板 |
| MC / 推流看画面 | ffmpeg 拉流、渲染输出 | ⚠️ 桌面能直接开浏览器看，方便 |

**结论：业务本身几乎不需要桌面。** 需要图形的地方，现网已经有 noVNC 通路了。

#### 那桌面真正的价值是什么？—— 带外管理

回到 8.7：笔记本没有 IPMI，**万一网络挂了，插上显示器只有文本控制台**。
但说实话文本控制台够用了：`journalctl` / `ip` / `nmtui` / `dmesg` 都在。
桌面多给你的其实只是一个「浏览器」—— 而这事你手机也能干。

**所以桌面的价值是「顺手」，不是「能不能修」。**

#### 三种情况怎么选

| 笔记本的定位 | 建议 |
|---|---|
| **纯服务器，平时不接显示器** | **Ubuntu Server，不装桌面**，省 1~1.5G 内存给 MC |
| **偶尔接显示器当控制台**（本方案默认） | Server + **轻量**桌面（XFCE / LXQt），**不要 GNOME** |
| **还要当日常电脑用** | Ubuntu **Desktop** 24.04，或按 4.3 走双系统 |

轻量桌面的装法：
```bash
sudo apt install xubuntu-desktop-minimal     # 或 lubuntu-desktop（更轻）
sudo systemctl set-default graphical.target
# 不想开机就进图形（省内存），保持 multi-user.target，
# 需要时 sudo systemctl start lightdm
```

#### ⚠️ 装了桌面，必须压住这四件事

Ubuntu Desktop 的默认行为对 7×24 服务器是**敌对**的，装了就一定要关：

```bash
# 1) snap 自动刷新 —— 会重启 snap 服务，专挑半夜
sudo snap refresh --hold

# 2) 文件索引器 —— 机器上有 1.3G MC 世界 + 3.6G docker 卷，扫一遍够 MC 卡一阵
sudo systemctl mask tracker-miner-fs-3 tracker-extract-3

# 3) 自动挂起 / 黑屏（8.1 的 logind 只管系统层，桌面要单独关；
#    下面这条要在图形会话里、以桌面用户身份执行）
gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-type 'nothing'
gsettings set org.gnome.desktop.session idle-delay 0

# 4) 自动更新后自动重启
sudo sed -i 's/^.*Unattended-Upgrade::Automatic-Reboot .*/Unattended-Upgrade::Automatic-Reboot "false";/' \
  /etc/apt/apt.conf.d/50unattended-upgrades
```

内存对比（大致值，用于判断值不值）：

| 配置 | 空载内存 |
|---|---|
| Ubuntu Server | ~400 MB |
| Server + XFCE（未启动图形会话） | ~450 MB |
| Xubuntu / XFCE 已登录 | ~900 MB |
| Ubuntu Desktop (GNOME) 已登录 | **1.3 ~ 1.8 GB**（再开浏览器 +0.5~1G） |

16G 上都装得下。但 **GNOME 是这里唯一「明显不值」的选项**：比 XFCE 多吃 0.5~1G，
换来的是你基本用不到的动效和集成。

#### 万一容器里的 QQ 不稳

`/home/wx/SnowLuma-v1.14.17-linux-x64` 是**原生 Linux 发行版**（带 `launcher.sh`），
可以脱离 Docker 直接跑。有人反馈 Electron 应用在真实 X 会话下比 Xvfb 里更稳 ——
如果容器里的 QQ 反复掉线，这就是 Plan B，而**桌面会让这个 Plan B 顺手很多**
（直接看到 QQ 窗口，不用再套一层 VNC）。这是「装桌面」最站得住的一条理由。

**装机当天必须做的硬件验证**（Linux 唯一的坑在这里）：
```bash
lspci -nnk | grep -iA3 net     # 确认无线网卡型号，查是否需要额外固件
iw dev                          # 确认 WiFi 接口名
# 连续 ping 网关 1 小时看丢包：WiFi 驱动不稳的话现在就该发现
ping -i 1 -c 3600 <网关IP> | tail -3
```

### 4.6 专门看「AI 直播 MC + 好友进服」这个场景

直觉会说：「MC 是游戏、直播要图形，那肯定得 Windows」。**读完代码后这个直觉是错的。**

#### 关键：这套直播栈根本不碰 GPU，也不碰图形栈

`/home/wx/mc/stream/render-stream.js` 的实际管线（读源码确认）：

```
mineflayer 读世界数据
   ↓
纯 JavaScript 体素光线投射（CPU，单线程）320×180
   ↓
node-canvas (Cairo) 合成 HUD / 中文字幕 / 缩放到 960×540
   ↓
ffmpeg -c:v libx264 -preset ultrafast -tune zerolatency   ← 软件编码
   ↓
FLV → RTMP → B站
```

**没有 WebGL、没有 headless-gl、没有 Chrome/puppeteer、没有 X11 依赖、显卡完全不参与。**
所以「Windows 图形生态好、驱动全」这个最常见的理由，在这个场景里**不适用**。

#### 三件对这个场景特别重要的事，Linux 全占

| 需求 | 为什么 Linux 更好 |
|---|---|
| **好友随时能进服** | 这要求 7×24 在线。Windows Update 半夜自动重启 = 好友连不上，而且直播会直接断流掉观众。 |
| **直播不掉帧** | 渲染是**纯 CPU 且单线程**。实测日志：`投射 111ms + 合成 27ms`，目标 5fps 实际只有 **4.7fps**。Windows 的 Defender 实时扫描（MC 世界 1.3G）、Search Indexer、Update 会直接抢这些毫秒。 |
| **迁移成本** | `mc.sh` / `bot.sh` / `stream.sh` 全是 bash + systemd。搬 Linux 是复制，搬 Windows 是重写。 |

#### Windows 的三个「优势」，逐条核对

1. **「中文字体不用装」** —— `render-stream.js:397` 硬编码了 `"Noto Sans CJK SC"`。
   本机实测 `fc-match "Noto Sans CJK SC"` → `NotoSansCJK-Regular.ttc`，**已装且命中正常**。
   这条**不成立**。（全新装的 Linux 记得 `apt install fonts-noto-cjk`。）
2. **「node-canvas 要好装」** —— 当前 `canvas@3.2.3`，Windows/Linux 都发预编译包，**无差异**。
3. **「硬件编码 NVENC/QSV 方便」** —— Windows 确实更顺，**但现管线用的是 libx264 软编**，
   压根没用到硬件编码。这条现在也不成立（真要上 NVENC，Linux 装好驱动一样能用）。

#### 唯一真正属于 Windows 的便利

**想在同一台机器上一边让 AI 直播、一边自己开 MC 客户端和它一起玩** ——
那有桌面确实方便（Linux 装个 XFCE 效果一样，见 4.5）。

#### 好友进服这件事，与操作系统无关

那纯粹是网络问题：端口映射 / IPv6 / WireGuard 中转，见 5.2。
Windows 和 Linux 在这上面**没有任何差别**，Windows 防火墙还多一步。

> **结论：Linux。** 而且这个场景下 Linux 的优势比一般情况下**更硬** ——
> 它的两个核心诉求（7×24 在线、CPU 独占给渲染）恰好都是 Windows 的弱项。

#### 顺带的优化机会

现在卡在单线程光线投射（111ms/帧）。搬到 16 核笔记本后：
- 单核性能远强于这台共享的 Xeon → 帧时间直接下降
- 可以调高 `stream-config.json` 的 `rw`/`rh`（投射分辨率）与 `fps`，画质立刻上一个档
- 仍嫌 CPU 贵，可以用 `worker_threads` 把射线分片并行 —— **这才用得上 16 核**

#### 直播观感：现在是「文字 HUD」，可以升级成原版界面

### 4.7 如果以后要直播星露谷物语

**结论：Linux 满足**，而且星露谷有**官方 Linux 原生版**
（[ConcernedApe 2016-07-29 公告](https://www.stardewvalley.net/stardew-valley-now-available-for-mac-linux/)，
Steam 与 GOG 均提供），**不需要 Wine / Proton**。

但要先认清：**这跟 MC 直播不是同一条路。**

| | MC（现状） | 星露谷物语 |
|---|---|---|
| 游戏本体 | **根本不运行** —— mineflayer 直接跟服务端协议对话 | **必须真的把它跑起来** |
| 画面来源 | 自研 CPU 体素光追（320×180） | 游戏自己的 OpenGL 窗口 |
| 抓取方式 | 无需抓取 | `ffmpeg -f x11grab` 或 OBS |
| 自动化 API | ✅ mineflayer（成熟） | ⚠️ 只有 [SMAPI](https://smapi.io/)，要自己写 mod |
| 输出规格 | 960×540 @ 5fps | 720p ~ 1080p @ 30fps |

MC 直播之所以便宜、之所以在这台 2 核机上还能跑，**核心原因是它压根不运行游戏**。
换成星露谷，就是从「无头数据流」跨到「真实 GUI 游戏」，复杂度不是一个量级。

#### 拆成两个问题

**A. 只是把画面直播出去**（你玩 / 挂机 / 展示）—— Linux 完全够：

```bash
# 无头 X（本机已有先例：Xvfb 正在跑 :1 和 :99）
Xvfb :1 -screen 0 1280x720x24 &
DISPLAY=:1 <启动星露谷>
ffmpeg -f x11grab -video_size 1280x720 -framerate 30 -i :1 \
       -c:v libx264 -preset veryfast -b:v 4000k -f flv <B站推流地址>
```

或直接用 **OBS Studio**（Linux 版很成熟）。有显卡就换 NVENC / QSV 编码。

**B. 要 AI 自己玩** —— **已有现成项目，而且是专为 DSH 写的**，不必从零造。

> **`rottenpen/agent-stardew`** · [GitHub](https://github.com/rottenpen/agent-stardew)
> 「星露谷农场小助手：Jev 自主游玩、dsh 插件、独立 CLI 与 SMAPI Mod」

它的架构正好卡在你的技术栈上：

```
mods/AgentStardew        SMAPI Mod（C#），在游戏主线程执行动作，
                         通过 WebSocket ws://127.0.0.1:17655/ 暴露「观察 + 动作」
packages/protocol        协议定义
packages/cli             独立 CLI（snapshot / doctor）
packages/dsh-plugin      ★ 注册 dsh 工具 + 自带 stardew skill，
                         Jev 控制器持有自主循环；面板在 dsh Web UI 的 /stardew
```

**它就是一个 dsh 插件** —— 装进你已经跑着的 DSH 里，Web UI 右上角多一个「农场小助手」。
用户给一次目标，Jev 持续选择并执行下一步，阶段结果回到原聊天。

**兼容性实测**（本机）：

| 项 | agent-stardew 要求 | 本机 | 结论 |
|---|---|---|---|
| dsh | 验证基线 `0.1.5-rc.1` | **`0.1.5-rc.2`** | 只差一个补丁，**基本对得上** |
| Node | 22+ | v24.19.0 | ✅ |
| .NET SDK | .NET 6 SDK（编译 Mod） | **未安装** | 需补装 |
| 游戏 | Stardew Valley 1.6.15 + SMAPI 4.5.2 | 待装 | — |
| 模型 | OpenRouter API Key（自主游玩） | 需自备 | 与 DSH 的模型分开计费 |

**三个要点：**

1. **有 mock 模式** —— `pnpm start --mock --jev` 能**不装游戏**先跑通整条 agent 链路。
   所以你可以**现在就先验证 rc.2 兼容性**，不用等游戏和 .NET 到位。这是最省事的起手式。
2. **编译基线是 macOS**（`--game-path "/游戏目录/Contents/MacOS"`）。
   SMAPI / C# 本身支持 Linux，但 Linux 上构建要改路径，**你会是较早踩这条路的人**。
3. **项目自述是「可操作的开发版」**，完整真实游戏验收「仍待完成」。
   所以它是**起点**，不是一个装完就能播的成品。

**其他可参考的路线**（MCP 风格，可用 dsh 现有的 MCP 接入）：

- [Hunter-Thompson/stardew-mcp](https://github.com/Hunter-Thompson/stardew-mcp)
- [amarisaster/StardewValley-MCP](https://github.com/amarisaster/StardewValley-MCP)
- 另外还有 [NagiBridge](https://github.com/anqinou-art/NagiBridge)

#### 这条路对系统选型的影响：**不变，甚至更偏 Linux**

- **无头跑 GUI 游戏**：Linux 用 Xvfb 即可，**不需要有人登录**；
  Windows 上 GUI 程序要求有交互式桌面会话，做无头 AI 驱动反而更别扭。
- agent-stardew 明确写了「Mod 支持失焦后台运行，后台游戏时间会继续推进」——
  这正是无头场景要的特性。
- 所以：**Linux 是这条路的顺风方向**，不是障碍。

#### 建议的落地顺序

1. **`--mock` 先跑通 dsh 插件链路**（不需要游戏、不需要 .NET）→ 验证 rc.2 兼容性
2. 装 SDV（**GOG DRM-free 离线包**，避开 Steam 客户端的无头登录麻烦）+ SMAPI + .NET 6 SDK
3. 编译 Mod（可能要针对 Linux 调构建路径）
4. 无头运行 + `x11grab` 推流

#### Linux 上的三个技术要点

1. **OpenGL**：SDV 是 2D 像素游戏，很轻。笔记本有真显卡 → 原生硬件 GL；
   即便无头，Mesa 的 `swrast` / `llvmpipe` 软件渲染也够（本机已确认存在 `swrast_dri.so`）。
2. **Steam 在无头环境很麻烦**（GUI 客户端 + 登录 + 2FA）。
   **建议用 GOG 的 DRM-free 离线安装包**，不依赖客户端常驻。
3. **编码压力比 MC 大得多**：从 320×180@5fps 变成 720p~1080p@30fps。
   16 核够用；有独显就上 NVENC。

#### 对方案的影响

- 16 核 16G 同时跑「MC 光追 + 星露谷 + 两路推流」够用，但**两个都是实时任务** ——
  建议用 `taskset` / `nice` 把核隔开，别让它们互相抢
- 内存预算里给 SDV 留 ~1G（含编码缓冲）
- **务实建议：先把 MC 那套跑稳，再加 SDV。** 若只做「直播画面」不做「AI 玩」，
  Linux 上就是十行 OBS / x11grab 配置的事

#### 还是 Linux 吗？

对 SDV 这**单项**，Windows 确实更省事（原生桌面、OBS 游戏捕获成熟、「装完就玩」）。
但为它换掉整个系统，代价是把 MC 那套 + QQ/Docker 那套全推到未验证的路径上。
而 4.5 已经说过，Linux 装个 XFCE 就有桌面。**结论不变。**

## 5. 网络方案（本方案真正的难点）

笔记本走 WiFi 意味着**没有公网 IP、在 NAT 后面**。而你现在有 4 样东西需要从公网可达：
`anihub.xin`(443)、Minecraft(25565)、bot viewer(3200)、SSH(22)。

**思路：把「公网入口」和「业务算力」拆开。** 服务器当地址，笔记本当机房。

### 5.1 隧道：WireGuard

> **先澄清一个常见误解：WireGuard 不是「内网穿透」。** 它是 **VPN / 组网**工具 ——
> 把几台机器连成一个虚拟内网。区别在于**谁需要公网 IP**：
>
> | 类别 | 代表 | 解决什么 | 需要公网 IP |
> |---|---|---|---|
> | VPN / 组网 | **WireGuard**、OpenVPN | 把多台机器连成虚拟内网 | **至少一端可达** |
> | 内网穿透 | frp、ngrok、rathole | 把内网端口暴露到公网 | 一台公网**中转机** |
> | 打洞型组网 | Tailscale、ZeroTier | 自动 NAT 打洞，打不通就中继 | 不需要 |
>
> **本方案能用 WireGuard，正是因为服务器有公网 IP。** 笔记本在 NAT 后主动向
> `139.196.173.199:51820` 发起握手，服务器从包的源地址就学到了笔记本的
> `公网IP:端口`，之后就能反向发包 —— 于是**只有一端需要公网**，双向就通了。
> NAT 映射会过期，这正是 `PersistentKeepalive = 25` 存在的理由（每 25 秒续一次命）。
>
> 反过来说：**如果两端都在 NAT 后面、都没有端口映射，WireGuard 是连不上的**
> —— 那种情况才需要 Tailscale / ZeroTier / frp。
>
> 另外，**WireGuard + nftables DNAT（即 5.2 方案 C）实际上就是自己搭的一套内网穿透**，
> 而且比 frp 更通用、更安全。

用 WireGuard 把两边连成 `10.77.0.0/24` 内网：

#### 先装工具（服务器和笔记本都要）

WireGuard 分两部分，好消息是**大头已经在内核里了**：

| 部分 | 状态 |
|---|---|
| 内核模块 | ✅ **已内置**。Linux **5.6**（2020-03）起进主线。实测本机 `6.8.0-63-generic` 的 `wireguard.ko.zst` 就在 `/lib/modules/6.8.0-63-generic/kernel/drivers/net/wireguard/` 下，version 1.0.0。**不需要 DKMS、不需要内核头文件、不需要编译。** |
| 用户态工具 `wg` / `wg-quick` | ⬜ **要装**，包名 `wireguard-tools`，很小 |

```bash
sudo apt install wireguard        # 元包，实际就是拉 wireguard-tools
wg --version                      # 验证
sudo modprobe wireguard && lsmod | grep wireguard
```

**服务器目前没装**（`which wg` 为空），**两台都要装** —— WireGuard 是对等协议，
没有「服务端 / 客户端」之分，两边跑同一个内核模块、同一套工具，配置里的差异只是「谁主动连谁」：

| | 服务器 (10.77.0.1) | 笔记本 (10.77.0.2) |
|---|---|---|
| 内核模块 | ✅ 已内置（6.8.0-63） | ✅ 已内置（Ubuntu 24.04 = 6.8） |
| `wireguard-tools` | ⬜ 要装 | ⬜ 要装 |
| `ListenPort` | ✅ 51820（等人来连） | ❌ 不需要 |
| `Endpoint` | ❌ 不需要 | ✅ 指向服务器公网 IP |
| `PersistentKeepalive` | ❌ 不需要 | ✅ 25（在 NAT 后**必须**） |
| 开机自启 | `wg-quick@wg0` | `wg-quick@wg0`（**别忘**，否则重启后隧道自己不起来，而你正好在外面） |

```bash
# 两台都执行
sudo apt install wireguard
sudo systemctl enable --now wg-quick@wg0      # 配置文件 /etc/wireguard/wg0.conf
```

> **不是所有设备都要装**：要「进入」这个虚拟内网的才需要（笔记本、以后可能用手机 SSH）。
> 只想偶尔连一下、不想装 WG 的电脑，用服务器当跳板即可（见 5.5 的 ProxyJump），
> 那台电脑完全不需要 WireGuard。

**三个坑：**
- **`DNS=` 那一行**：`wg-quick` 会调 `resolvconf`。本机有（`/usr/sbin/resolvconf`），
  但全新安装的笔记本要先 `which resolvconf` 确认；没有就 `sudo apt install resolvconf`，
  或者干脆**不写 `DNS=`**（本方案里它是可选的，隧道只用内网 IP）。
- **UDP 51820 要放行两处**：`sudo ufw allow 51820/udp` **且** 阿里云**安全组**放行。
  安全组是前置的 —— 只放 ufw 一样不通，这是最常见的「配好了却握手不上」原因。
- **`net.ipv4.ip_forward=1`**：只有做 5.2 方案 C（MC 四层转发）时才需要。

**服务器端** `/etc/wireguard/wg0.conf`：
```ini
[Interface]
Address = 10.77.0.1/24
ListenPort = 51820
PrivateKey = <服务器私钥>

[Peer]                      # 笔记本
PublicKey = <笔记本公钥>
AllowedIPs = 10.77.0.2/32
```

**笔记本端**：
```ini
[Interface]
Address = 10.77.0.2/24
PrivateKey = <笔记本私钥>

[Peer]                      # 服务器
PublicKey = <服务器公钥>
Endpoint = 139.196.173.199:51820
AllowedIPs = 10.77.0.1/32
PersistentKeepalive = 25    # ← 关键：笔记本在 NAT 后，靠它维持映射
```

要点：
- **`PersistentKeepalive = 25` 不能省** —— 否则笔记本侧 NAT 映射过期，服务器就找不到它。
- 阿里云**安全组**必须放行 `UDP 51820`（ufw 放行不够，安全组是前置的）。
- 国内家宽到阿里云的 UDP 有时被 QoS，若不稳定 → 备选 **Tailscale**（自动 NAT 打洞，零配置，
  代价是多一个第三方依赖）或 **ZeroTier**。
- 隧道只承载控制面和小流量。**大流量（MC、推流）尽量不走隧道**，见 5.2。

### 5.2 Minecraft 的玩家入口：四个选项（按优先级）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 家里端口映射 + DDNS** ⭐ | 路由器 25565 → 笔记本，加 `mc.anihub.xin` 动态解析 | MC 流量**完全不过服务器**，延迟最低，服务器零带宽 | 需要公网 IPv4 + 路由器权限 |
| **B. IPv6 直连** | 家宽普遍有 IPv6；加 `AAAA` 记录 + `SRV`，玩家连 `mc.anihub.xin` | 也不需要服务器转发，且绕过 CGNAT | 玩家侧要有 IPv6；家宽前缀会变，需 DDNS |
| **C. 服务器四层转发** | 服务器 `nftables` 把 25565 DNAT 到 `10.77.0.2:25565` | 不需要家里任何权限，玩家无感 | MC 流量吃 ECS 带宽（按量计费的话烧钱）；多一跳延迟 |
| **D. frp / playit.gg** | 笔记本主动把端口映射到公网中转 | 免公网 IP，配置简单 | 第三方依赖；免费档有带宽/延迟限制 |

**推荐：先试 A，不行退 B，都不行才用 C。**
用 C 的话加大约 1~5ms（取决于你的城市到上海阿里云的 RTT），MC 可接受。

方案 C 的 nftables 片段（服务器上）：
```nft
table ip mc {
  chain prerouting {
    type nat hook prerouting priority -100;
    tcp dport 25565 dnat to 10.77.0.2:25565
  }
  chain postrouting {
    type nat hook postrouting priority 100;
    oifname "wg0" masquerade
  }
}
```
加 `net.ipv4.ip_forward=1`。

> **重要**：无论选哪个方案，**B站推流都必须从笔记本直连出站**，绝不能绕服务器 ——
> 那是持续上行流量，走 ECS 会立刻吃满带宽额度。

### 5.3 nginx 改造（服务器上）

只改 `proxy_pass` 的目标，TLS/证书/域名全不动：

```nginx
server {
    listen 443 ssl http2;
    server_name anihub.xin;

    # 原来：proxy_pass http://127.0.0.1:3001;
    location /        { proxy_pass http://10.77.0.2:3001; }
    location /mc/     { proxy_pass http://10.77.0.2:3200/; }
    # ... 其余 location 同样把 127.0.0.1 换成 10.77.0.2

    # 建议加：隧道断了要快速失败，不要挂住连接
    proxy_connect_timeout 5s;
    proxy_read_timeout    60s;
}
```

建议再加一段隧道健康检查（可选）：笔记本若掉线，nginx 返回 502；可以配一个静态降级页，
避免访客看到 nginx 默认错误页。

### 5.4 带宽核算（搬家前必测）

在笔记本上测：`speedtest` 或 `curl -o /dev/null <大文件>` 测**上行**。
- B站 640×360 推流 ≈ **1~2 Mbps**
- MC 每玩家 ≈ 0.1~0.5 Mbps（区块加载时会有突发）
- 取图/爬虫/embedding 下载 ≈ 间歇性

#### ⚠️ 容易漏掉的大头：`/mc/` 那个网页地图

`https://anihub.xin/mc/` 是 **Prismarine Viewer** —— AI 玩 MC 的实时网页地图，
由 `botd.js` 提供（对外 3200，viewer 本体 3201），nginx 带 WebSocket 升级转出去。

**2026-10-03 实测**（连上 viewer 数了 12 秒的 socket.io 流量）：

```
事件统计: entity 2233 次 / position 285 次 / loadChunk 24 次 /
          blockUpdate 16 次 / unloadChunk 12 次
12 秒总计 2.35 MB  →  1.64 Mbps
```

它推的不是图像，而是**世界数据**（实体、坐标、区块变更），浏览器本地用 three.js 渲染。
但流量是实打实的：**一个观看者 ≈ 1.6 Mbps 持续**，和 B站推流同一个量级。

**这意味着**：搬到笔记本后，只要有人通过公网域名看这个地图，链路是

```
浏览器 → 服务器 nginx(443) → WireGuard 隧道 → 笔记本 botd(3200)
```

**全程吃 ECS 带宽。** 建议：

- **自己看的时候直连隧道**：`http://10.77.0.2:3200`（或 Tailscale 地址），完全不经过服务器
- nginx 的 `/mc/` 保留给「偶尔给别人看」，别自己天天开着
- 若不打算对外开放，**直接删掉 nginx 的 `/mc/` location 和 ufw 里的 3200 规则**
- viewer 可以关：`VIEWER=0`（见 botd.js），排查负载时有用

**结论：家宽上行 ≥ 10 Mbps 才能舒服地跑「推流 + 地图 viewer + 几个 MC 玩家」。**
只有 5 Mbps 的话这三样会互相挤 —— 那就降低推流码率、或少开 viewer。

### 5.5 远程登录：从任何地方管这台笔记本

先看清楚你现在怎么用的（`last` 实测）：你从 `223.104.155.190`(移动)、`183.211.200.18`(电信)、
`124.70.231.62`(华为云) **多个不同网络** root 登录这台服务器，并靠 tmux 保持长会话
（当前有两个 tmux：09-23、09-24 建的）。所以问题不是「能不能登录」，而是
「**从这些地方还能不能登录**」。

**能，而且比现在更好管** —— 因为 WireGuard 是**笔记本主动连出去**的。隧道一旦建立，
无论你在家、在公司、还是开手机热点，都能直接摸到它。

#### 三条路径，按推荐度

| 场景 | 做法 |
|---|---|
| **在家（同局域网）** | `ssh wx@192.168.x.x` 直连。**必须给笔记本配静态 IP 或路由器 DHCP 保留**，否则重启后 IP 一变你就找不到它。 |
| **在外（推荐）** | 先连服务器的 WireGuard，再 `ssh 10.77.0.2`。 |
| **在外（本地不想装 WG 客户端）** | 用服务器当跳板机，一条命令直达 ↓ |

```bash
# 本地 ~/.ssh/config —— ProxyJump 一跳直达
Host laptop
    HostName 10.77.0.2
    User wx
    ProxyJump root@139.196.173.199

# 或直接命令行
ssh -J root@139.196.173.199 wx@10.77.0.2
```

ProxyJump 的好处：服务器只做 TCP 转发，**你的私钥不落在服务器上**，认证端到端。
你现有的那把密钥 `ran@DESKTOP-OTSGR0E`（Windows 桌面）可以直接复用 ——
把公钥加进笔记本的 `~/.ssh/authorized_keys` 就行，客户端体验完全不变。

#### 更省事的备选：Tailscale

不想维护 WireGuard 配置文件的话，**Tailscale 最省心**：笔记本、手机、Windows 桌面各装一个
客户端、登同一账号，之后 `ssh 笔记本主机名` 从任何地方可用 —— NAT 打洞全自动，
不需要公网 IP、不用改路由器。代价是多一个第三方依赖（且它自己要能连上协调服务器）。
**两者可以共存**：日常用 Tailscale 顺手，关键链路用 WG 兜底。

#### 不建议的做法

- **家里路由器把 22 端口映射到公网** —— 等于把笔记本 SSH 摆到全网扫描器面前。
  除非你同时做了「仅密钥登录 + 禁 root + fail2ban + 改端口」，否则别开。
- **反向 SSH 隧道**（笔记本 `ssh -R` 到服务器）—— 与 WireGuard 功能完全重叠，
  且断了不会自动重连（得配 `autossh`），没必要。

#### ⚠️ 顺带一个必须修的问题

现在这台服务器是 **`PermitRootLogin yes` + `PasswordAuthentication yes`**，
22 端口对全网开放 —— 这是最典型的被爆破目标，`journalctl -u ssh` 里大概率已经有一堆失败尝试。
搬到笔记本后**不要复制这个配置**：

```bash
# 笔记本 /etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
ListenAddress 192.168.x.x      # 只监听局域网
ListenAddress 10.77.0.2        # 和 WireGuard
```
**路由器上不要给笔记本做 22 端口映射。** 要从公网进就走 WireGuard 或 ProxyJump。

## 8. 笔记本当 7×24 服务器的调优

这部分不做，笔记本会在三天内以各种方式"自己关机"。

### 8.1 合盖不休眠（必做）
```bash
sudo sed -i 's/^#\?HandleLidSwitch=.*/HandleLidSwitch=ignore/' /etc/systemd/logind.conf
sudo sed -i 's/^#\?HandleLidSwitchExternalPower=.*/HandleLidSwitchExternalPower=ignore/' /etc/systemd/logind.conf
sudo systemctl restart systemd-logind
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

### 8.2 WiFi 关省电（必做）
不关的话，无线网卡会在空闲时降功耗，带来几十到几百毫秒的延迟尖峰 —— MC 玩家会看到
「挖方块没反应」，推流会卡顿。
```bash
# 立即生效
sudo iw dev wlan0 set power_save off
# 持久化（NetworkManager）
sudo tee /etc/NetworkManager/conf.d/wifi-powersave-off.conf <<'EOF'
[connection]
wifi.powersave = 2
EOF
sudo systemctl restart NetworkManager
# 验证应为 "Power save: off"
iw dev wlan0 get power_save
```
> 网卡名不一定是 `wlan0`，用 `iw dev` 查。
> 如果笔记本有网口 —— **强烈建议插网线**。这一条能消掉一半的稳定性风险。

### 8.3 电池（关乎安全，不是性能）
长期插电 + 满电，锂电池会鼓包。笔记本 7×24 插电必须设充电阈值：
```bash
# 内核支持时（多数 ThinkPad / 部分华硕、联想）
echo 60 | sudo tee /sys/class/power_supply/BAT0/charge_control_end_threshold
```
不支持就装 `tlp`：
```bash
sudo apt install tlp && sudo tlp setcharge 60 80 BAT0
```
**阈值设 60~80%，不要让电池长期停在 100%。**

### 8.4 散热
笔记本散热能力远不如服务器，16 核持续满载会热节流（性能反而掉一半）。
- 垫高机身、清灰、必要时换硅脂
- 监控：`sensors`（`lm-sensors` 包），确认满载温度 < 90°C
- 放通风处，别塞柜子里
- 如果 MC + 推流同时满载就撞温度墙 → 给 `ffmpeg` 限核（`taskset`）或降推流分辨率

### 8.5 文件系统与写入
- 根分区开 `noatime`，减少无谓写入
- journald 限容：`/etc/systemd/journald.conf` 里 `SystemMaxUse=500M`
- MC 日志、`state/bridge.log` 配 logrotate
- 用 SSD；如果是机械盘，MC 世界加载会很痛

### 8.6 断电保护（建议）
家里停电 = 全部业务停。有条件配个小 UPS（或笔记本**保留电池**本身就相当于 UPS ——
这也是不拔电池的另一个理由）。掉电后要能自动恢复：确认所有服务都是 `enabled` 且有
`Restart=always`，BIOS 里设「来电自动开机」。

### 8.7 带外管理：笔记本最大的短板

**这是笔记本和云服务器最关键的区别，必须提前接受：**

| | 阿里云 ECS | 家中笔记本 |
|---|---|---|
| 宕机后还能进去吗 | ✅ 控制台 VNC / 串口 | ❌ **只能人到现场** |
| 远程强制重启 | ✅ 控制台 | ❌ 除非接智能插座 |
| 换系统 / 救砖 | ✅ 挂载 ISO | ❌ 要插 U 盘、接显示器键盘 |

笔记本没有 IPMI/BMC。一旦出现**内核 panic、WiFi 驱动崩溃、系统卡死**，
WireGuard、SSH、Tailscale **全部无效**，你只能回家。

**最低成本的兜底：一个 WiFi 智能插座 + BIOS 设「通电自动开机」。**
- 笔记本电源接在智能插座上（充电器常插，配合 8.3 的充电阈值）
- BIOS 里把 `AC Power Recovery` / `Power On After Power Failure` 设为 **On**
- 出事时手机 App 断电 10 秒再通电 → 自动开机 → 所有 systemd 服务自动拉起
- 成本几十块，能覆盖 90% 的「死机」场景

**它救不了的情况**（要提前想清楚）：
- 网卡驱动崩了但系统还活着 → 断电重启能救（重载驱动）✅
- 系统起不来（升级把内核搞坏了）→ 插座救不了 ❌，得接显示器
- 硬盘坏了 → ❌

所以：**笔记本要放在方便你偶尔接显示器键盘的位置**，别塞到够不着的柜子里。
这也正是第 9 节强调**每日异地备份**的原因 —— 硬件故障时，服务器上那份副本就是退路。

## 9. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| **WiFi 抖动 / 丢包** | MC 卡顿、推流掉帧、QQ 消息延迟 | 优先插网线；关省电；5GHz 固定信道；贴近路由器 |
| **家宽上行不足** | 推流与 MC 互挤 | 搬家前测上行（5.4）；必要时降码率 |
| **无公网 IP / CGNAT** | MC 玩家连不上 | 5.2 的 A→B→C→D 逐级降级 |
| **WireGuard UDP 被 QoS** | 隧道时断时续 | 备选 Tailscale/ZeroTier |
| **QQ 换机触发风控/需重新登录** | 桥接中断数小时 | 低峰期迁移；备好扫码通道（noVNC）；**绝不双开** |
| **B站推流需重新人脸核验(60043)** | 直播中断，须手机操作 | 迁移时手机在手边；提前在 App 里触发一次核验 |
| **笔记本硬件故障 = 全站下线** | 单点风险（原来服务器也是单点） | 每日异地备份；服务器保留 world 副本；关键配置全部入 git |
| **磁盘故障** | 数据丢失 | 备份到服务器；world 用 `tar` 定时快照 |
