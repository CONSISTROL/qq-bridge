# 群知识库（问题 → 答案）

> 目标：**同一个问题被不同的人反复问到，不重复考据、不给出两套答案。**
> 黑话库管「这个词什么意思」，知识库管「这个问题的答案是什么」——两者分开存储、分开检索。

## 它解决什么

群里必然会反复出现同一批问题：某个东西什么时候发布的、某人是谁、某个操作怎么弄、群的规矩是什么。
没有知识库时，每个人问一次都要重新搜一遍、重新组织一遍语言，还可能这次说 A、下次说 B。

知识库把这些沉淀成条目，**换着说法问同一件事也会命中同一条**，并会告诉你这条已经被问过多少次。

两件事同等重要：

- **该记就记**：只要以后可能用得上就存，不必等到「被问了很多次」。去重是自动的，重叠的知识会合并而不是堆条目。
- **反复问到的就更新**：同一条被反复问到时，答案会随着新信息被替换（新版本号、新价格、更准的结论），
  `revision` 记录改过几次。它不是「一次写死的 FAQ」，而是一条会被持续修正的条目。

## 数据与文件

| 内容 | 位置 |
|---|---|
| 条目本体 | `state/knowledge.json`（数组，权限 0600，原子写） |
| 向量索引 | `state/knowledge-vectors.json`（独立于黑话的 `slang-vectors.json`） |
| 代码：存储与去重 | `src/knowledge-store.js` |
| 代码：桥接集成 | `src/bridge.js`（检索、HTTP 端点、提示注入） |
| 代码：AI 工具 | `src/mcp-snowluma-safe.js`（`qq_knowledge_query` / `qq_knowledge_submit`） |
| 控制台 | `public/console/views/knowledge.{html,js}` |

### 条目结构

```json
{
  "id": "kmue5u44w-k44f4s",
  "question": "DeepSeek 是什么时候开源的？",
  "answer": "2023 年 11 月发布并开源。",
  "kind": "fact",                  // fact | rule | person | howto
  "tags": ["fact", "人工智能"],
  "aliases": ["ds 啥时候开源的"],   // 其他问法，便于合并命中
  "sources": ["https://..."]       // 只收 http(s)，便于以后核对
  "status": "confirmed",           // candidate | confirmed | archived
  "hitCount": 3,                   // 被问过多少次
  "askers": ["甲", "乙"],          // 多少个不同的人问过
  "revision": 2,                   // 答案被更新过几次
  "conflict": null                 // 非空 = 有待裁定的答案冲突
}
```

## 去重是怎么做的

三层，从便宜到贵：

1. **问题指纹**（`questionFingerprint`，纯确定性，无模型）
   统一字符 → 去掉空白/标点 → 删掉句中疑问填充词（`是什么时候`/`怎么弄`/`能不能`…）→ 剥掉首尾客套与语气词（`请问`/`吗`/`的`…）→ 同义疑问词归一（`哪年`→`何时`）。
   于是 `DeepSeek 是什么时候开源的？` 和 `deepseek 什么时候开源的` 得到同一个指纹 `deepseek开源`，直接合并。

2. **字面相似度**（`questionSimilarity`）
   bigram Jaccard 与编辑距离相似度取较大值，默认门槛 0.62。指纹不同但只差一两个字的（`今天股市怎么样` / `今天大盘怎么样`）会合并。

3. **别名**：条目可以带 `aliases`，命中即合并。

三层都没命中，才新建条目。字面完全不像的（`群里管理员是哪一位` vs `管理员是谁`）交给向量检索兜底，不做硬合并——**宁可多一条可人工合并，也不要误并把答案张冠李戴。**

## 重复问题的提醒

`hitCount ≥ knowledge.remindHitCount`（默认 3）**且** `askers ≥ knowledge.remindMinAskers`（默认 2）时：

- 注入的知识表里，该条后面会附一句「这条已被问过 N 次（M 个不同的人），直接照上面的答案回，别再重新查/重新编」；
- 唤醒提示里单独列一段「【这几条被反复问过，答案该准一点】」；
- `qq_knowledge_query` 的返回里有 `repeats` 数组。

要求「多个不同的人」是刻意的：同一个人反复问同一条，那是他个人没记住，不是群级 FAQ。

## 状态与「候选 → 确认」链路

三种状态，与黑话库（`src/slang-learner.js`）同一套语义：

| 状态 | 含义 | 参与检索/注入 |
|---|---|---|
| `candidate` | 待人工确认 | ✗ |
| `confirmed` | 已生效 | ✓ |
| `archived` | 人工停用（内容留着） | ✗ |

写入路径怎么决定状态：

- `autoWrite = true`（默认）：AI 提交直接落 `confirmed`。
- `autoWrite = false`：AI 提交落 `candidate`，等你在控制台点「确认生效」。
- **报冲突的条目一律落 `candidate`**，不管 `autoWrite` 开没开——AI 自己说这个答案存疑，就不能让它直接生效。
  已生效条目被报冲突时会**降级回候选**（这一步曾经漏在「命中已有条目」分支，导致存疑答案照样被注入）。
- 候选被再次提交只是补证据（`revision + 1`），**不会自己转正**——`autoWrite` 开着也不行，那等于绕过人工闸门。
- 控制台里编辑一条候选项 = 我确认过了，会顺手转正（否则你还得再点一次「确认生效」，多数人不会想到）。

候选/停用条目**不参与向量索引**（`state/knowledge-vectors.json` 只收生效条目），
所以「确认」之后需要一次索引补齐——`markKnowledgeDirty` 会自动调度，也可以手动点「补齐向量索引」。

## 写入策略（默认全自动，可随时人工删改）

`knowledge.autoWrite = true`（默认）时，AI 提交即入库生效。这有风险，所以配了几道保险：

1. **答案会持续更新，但拒绝明显更差的更新。**
   这条被反复问到时，答案本来就该被更新（新版本号、新价格、更准的结论），所以默认**接受覆盖**，
   只挡两种情况：
   - 复读凑长（`xxxxxxxx`、`哈哈哈哈`）：**用字极少却在凑长**的那种；
   - 大幅缩短（不足旧答案一半且至少少 15 字）：那多半是「随口一句」而不是「更新」。

   注意「用字更丰富」是好答案的特征，不是垃圾信号——早先版本的判据正好写反了，会把详细答案判成垃圾。
   每次真正替换答案会 `revision + 1`，控制台列表能看到「改过 N 次」——改得多的通常值得人工看一眼。
2. **冲突标记 + 降级候选**：AI 查询时会拿到 `similarity`，如果它发现某条已有答案与事实不符，可以在提交时带 `conflictOf=<该条 id>`。
   桥接会把该条标上 `conflict` **并降级为候选**（存疑答案不许继续注入）；
   控制台顶部单独一块列出「当前答案 vs AI 报告的另一答案」，等人工裁定——确认后转正、冲突标记清除。
3. **一键停用**：可疑条目可以停用（`status=archived`），立刻不进注入池、不参与检索，但内容留着。
4. **来源白名单**：只存 `http(s)://`，避免把任意字符串当链接注入。
5. **写入限频**：默认 15 次/分、60 次/时（比黑话宽松得多，因为一轮正经问答可能连续沉淀好几条）；
   分钟额度只防「瞬间刷库」，真正的护栏是小时额度。

把 `autoWrite` 关掉即回到「AI 只提交、人工确认」的保守模式：AI 写的条目会落成 `candidate`，
控制台「待确认候选」标签页里会堆着等你过一遍。

## 注入链路

每次唤醒/每条消息进来时（`withSlangContext`）：

1. 用当前消息文本编码成一个向量；
2. 在已生效条目里按语义相关性选 top-K（`knowledge.injectMax`，默认 6）；
3. 渲染成 `【群知识库】` 表格追加到提示词。

**与黑话的关键差别：知识库不做「按频次补位」。**
黑话表补几条高频词无伤大雅（看到常用词没有坏处），但答案补位会让 AI 拿到无关问题的答案——比「看不到」危险得多。
所以 `minFill = 0`：没有语义相关的条目就一条都不注入。

启动时会预热一次（`warmKnowledgeIndex`），失败只记日志，不影响回复。

## 配置

```jsonc
"knowledge": {
  "enabled": true,
  "injectMax": 6,            // 每次注入最多几条
  "autoWrite": true,         // AI 提交即生效；false = 落成 candidate 等人工确认
  "remindHitCount": 3,       // 命中提醒阈值
  "remindMinAskers": 2,      // 且至少几个不同的人问过
  "similarityThreshold": 0.62, // 字面近重复合并门槛
  "conflictMinCosine": 0.8     // （预留）语义冲突判定门槛
}
```

工具开关：`socialV2.tools.knowledge`（默认开）。

## 控制台

左侧「语料 → 群知识库」（`#/knowledge`）：

- 统计条：总数 / 已生效 / 累计命中 / 反复被问 / 待裁定冲突；
- 标签页：**已生效 / 待确认候选 / 待裁定冲突 / 已停用 / 全部**（候选和冲突是日常最需要打理的两个入口）；
- 列表按**被问次数**排序（最该保证准确的排前面），可搜问题/答案/别名/标签，可按类型（fact/rule/person/howto）筛选；
- 状态标签直接标在每行上（生效中 / 待确认 / 已停用 + 冲突待裁定），统计条会高亮「待确认 N 条」；
- 冲突单独置顶一块，可「去裁定（编辑）」或「保留当前、清除标记」；
- 行内动作：编辑、候选的「确认生效」、生效/停用的互切、删除，支持勾选批量删除；
- 参数区：开关、注入条数、提醒阈值、去重门槛、向量索引重建；
- 检索调试：输入一个群友可能问的问题，直接看**去重判定**（指纹/字面/语义命中哪条）、**会注入哪些条目**、以及**实际注入的提示词片段**。


`test-knowledge-e2e.mjs` 用 `QQ_BRIDGE_CONFIG` + `QQ_BRIDGE_STATE_DIR` 起隔离实例，不碰线上 bridge 与真 QQ。
注意它会在隔离状态目录里写 `mode.json`（`reserved2`）——DSH 不可达时桥接按本地模式兜底，
缺了它 `currentMode` 会回落成 `chat`，带 agent token 的 v2 接口会被模式闸门整体拒绝。

## 已知边界

- 知识库**不自动从群聊提取候选**（黑话库那套 `slang-learner` 是另一条链路）。目前靠 AI 在答完后主动沉淀。
  如果你希望「全新问题被问到第 N 次时自动提醒沉淀」，可以再加一个基于「同一指纹出现在最近消息里的次数」的触发
  ——现状是只有**已存在条目**被反复问到时才提醒。
- 指纹与字面相似度都是**确定性字符串规则**，不做同义词理解。真正换说法的合并靠向量检索命中后的 `similarity`，
  以及 AI 在提交时带 `aliases`。
- 答案更新只保留「当前版本 + 修订次数」，**不存历史全文**。需要版本历史的话得另做（存全文会让 state 文件快速膨胀）。
- `conflictMinCosine` 目前只是预留配置项：冲突靠 AI 主动报 `conflictOf`，桥接不会自己判定答案矛盾。
