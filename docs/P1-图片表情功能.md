## 一、P0：工具开关热更新（免重启 DSH）

**问题**：工具表是 MCP 子进程启动时一次性注册的，控制台改开关后模型侧看不到变化，必须重启 DSH。

**改动**（`src/mcp-snowluma-safe.js`）：
- 所有注册统一走 `defineTool()`，拿到 `RegisteredTool` 句柄（支持 `remove/enable/disable`）。
- 注册整体包成 `registerAllTools()`：先 `removeAllTools()`，再按最新 `cfg` 重跑注册。
- `fs.watch(config.json)` + `fs.watchFile`（2s 轮询兜底）+ 300ms 防抖；内容指纹没变则跳过。
- 重注册完只发 **一次** `server.sendToolListChanged()`（批量期间屏蔽逐条通知，否则 36 个工具会打出几十条）。
- DSH 的 `@deepseek-ai/dsh-mcp-client` 本来就监听 `ToolListChangedNotificationSchema` 并会 `re-syncing`，所以**无需重启 DSH**。

**效果**：控制台开关工具 → 1~2 秒内模型工具表同步；DSH 只在**加载这份新代码时**需要重启一次。

**验证**：`node scripts/test-p0-hot-reload.mjs`（隔离副本 `/tmp/mcp-test`，不碰线上配置）
```
✅ 初始工具表包含 qq_get_self_image / qq_save_sticker（36 个）
✅ 关闭开关后工具消失（免重启）   ✅ 收到 list_changed ×1
✅ 重新打开后工具回来（免重启）   ✅ 收到 list_changed ×1
```

## 二、P1：`qq_save_sticker`（把外部图片存进 QQ 收藏表情库）

链路：**桥接自己下载 → 校验 → 转 base64 → 网关 `add_custom_face` → 得到 emoji_id → 之后用现成的 `qq_send_sticker` 发送**。

> 铁律：远程图片一律由桥接 `safeFetchBuffer()` 下载（DNS 固定 + 逐跳重定向校验 + 禁内网 + 格式/体积校验），
> **绝不把原始 URL 交给 OneBot 网关去抓**（那会绕过 SSRF/本地文件防护）。

### 支持的来源
| source | 说明 |
| --- | --- |
| `library`（默认） | `assets/stickers/` 下的**纯文件名**；带路径或 `..` 一律拒绝 |
| `base64` | `data:image/...;base64,...` 或裸 base64；校验确实是 PNG/JPEG/GIF/WebP |
| `url` | http(s) 图片直链；**默认关闭**，需 `socialV2.image.allowRemoteUrl = true`；命中 `refererAllow` 时自动带 Referer（B 站防盗链） |

### 开关与参数
- 工具开关：控制台 **07 二代仿真模式 → 工具开关 → `qq_save_sticker`**（`socialV2.tools.saveSticker`）
- 能力参数（`config.json` → `socialV2.image`）：
```jsonc
"image": {
  "enabled": true,
  "allowRemoteUrl": false,        // 默认只允许本地图库/base64
  "libraryDir": "assets/stickers",
  "maxBytes": 5242880,            // 5MB
  "maxPerMinute": 5,
  "maxPerHour": 30,
  "refererAllow": ["https://www.bilibili.com", "https://b23.tv"]
}
```

### 验证结果（`node scripts/test-p1-save-sticker.mjs`）
```
✅ 拒绝路径穿越            ✅ 图库缺图时报错        ✅ 拒绝非图片文件
✅ 拒绝非图片 base64       ✅ 默认拒绝远程 URL      ✅ 本地图库保存成功（返回 emojiId）
✅ 开启远程后仍拒绝内网地址（SSRF 防护）            ✅ 超过每分钟上限返回 429
```

## 五、P3：B 站抓图入库（`scripts/fetch-bili-images.mjs`）

### 三个图源的无登录可用度（2026-09 实测）
| 来源 | 接口 | 无登录 | 备注 |
| --- | --- | --- | --- |
| 评论区 | `x/v2/reply/wbi/main`（**需 wbi 签名**） | ✅ code=0 | 图在 `data.replies[].content.pictures[].img_src` |
| 动态 | `x/polymer/web-dynamic/v1/opus/feed/space`（wbi） | ✅ 20 条/页 | 每条有 `cover.url`；`opus/detail` 固定 **-352**，要登录 |

> 另外用 `x/frontend/finger/spi` 拿 `buvid3/buvid4` 作 cookie，能显著降低触发风控的概率。

## 九、故障复盘：桥接"忙"标记卡死（AI 不回话）

**症状**：日志反复出现 `[reserved2] 会话繁忙，暂存唤醒原因 …`，AI 再也不回话；DSH 侧转录里回合却早已 `turn/end reason=completed`。

**根因**：桥接判断"会话是否忙"靠内存标记（`v2TurnStartAt` / `collectors` / `promptQueues` / `pendingWakeKeys`）。
若**桥接在回合中途重启**，或 **DSH 重启导致终帧丢失**，这些标记会永久残留 → 后续所有唤醒只能排队，永远不投递。

**修复**：新增**忙标记看门狗**（`src/bridge.js`）——
- 排队时记录 `st.pendingSince`；真正放行唤醒时清零
- 每 60s 巡检：某会话排队超过 `socialV2.busyRecoveryMs`（默认 **480000 = 8 分钟**，设 0 关闭）就
  `forceClearBusyV2()` 清掉全部忙标记，并补投一次 `busyRecovery` 唤醒
- 启动日志会打印：`[reserved2] 忙标记看门狗已启动（8 分钟）`

**另外一个坑**：DSH 重启后**不要立刻**让桥接投递（会话可能还在 seeding），否则又会留下脏标记；看门狗现在会自动兜底。

**手动急救**（看门狗生效前/想立刻恢复）：

# 2) 手动唤醒积压的会话

## 十、故障复盘：大图发送失败（fetch failed / UND_ERR_SOCKET）

**症状**：`qq_send_image` / `qq_send_sticker` 偶发 `发送图片失败：fetch failed`；日志里 `工具发送表情失败 … fetch failed`。

**实测定位**：

| 路径 | 1MB body | 2MB body | 3.3MB body |
| --- | --- | --- | --- |
| 宿主 → `127.0.0.1:3000`（经 docker-proxy） | ✅ | ❌ `UND_ERR_SOCKET` | ❌ |
| 宿主 → 容器 IP `172.18.0.2:3000`（绕过 proxy） | — | — | ❌ `ECONNRESET` |
| **桥接 → OneBot WebSocket（3001）** | ✅ | ✅ | ✅ **成功** |

**结论**：**不是 docker-proxy**，是 SnowLuma 的 **HTTP 端点在请求体 ≥2MB 时会直接断连**。
而 base64 图片动辄 3~7MB（2.4MB 的 PNG → 3.1MB base64），所以大图必挂；小表情偶尔挂是同一原因的边缘抖动。

**修复**（`src/bridge.js`）：新增统一的 `postOneBot(action, params)`，
**优先走 OneBot WebSocket**（收藏表情的 base64 本来就一直走 WS，稳定），失败才回退 HTTP 并重试（300ms/900ms 指数退避）；
错误信息带底层 `cause.code` 便于定位。文字、图片、表情三条发送路径全部改走它。

**验证**：
```
send-image 发 2.4MB 评论图 → ok:true，messageId=-585133311（WS 返回结构已归一化）
让 AI 自己跑一轮 → 2 张评论图 + 1 个收藏表情 + 2 条文字，全部成功；WS 回退次数 = 0
```

> 若想更保守，可把 `socialV2.image.maxBytes` 从 5MB 降到 3MB；走 WS 后基本不需要。

## 十一、"GIF 发出来不动"的真相

**不是发送通道的问题，是图本身不是动图。**

诊断过程：
1. 精确解析用户看到的那张 `.gif`（B 站评论区图）：**`GIF89a`，300x323，帧数 = 1，总时长 0.0s，无循环标记** → 它就是个**单帧静态 GIF**。
2. 对比实测：B 站"大肥鱼 动图"搜索里，`.gif` 中确有 106 帧 / 32 帧 / 59 帧的真动图；也有 1 帧的静态图。**B 站评论区/专栏大量 `.gif` 是视频帧导出的静态图**。
3. 之前那个"128 帧"是我粗略数 `0x2C` 字节的误判（LZW 数据里也会出现该字节）。

**修复**：
- 新增 `src/image-meta.js`：按 GIF 块结构精确解析帧数（`gifFrameCount` / `isAnimatedWebp` / `describeAnimation`）。
- `qq_search_images` 新增参数 **`animatedOnly`**：逐张下载探测帧数，只返回真动图（实测把 6 张过滤成 2 张真动图）。
- `qq_send_image` / `qq_save_sticker` 的返回里带上 `animated` / `frames`；发到单帧静态 `.gif` 时桥接日志会提示
  `[image] 注意：… 是单帧静态 .gif（不会动）`。
- MCP 工具描述里也加了提醒：需要动图请传 `animatedOnly: true`。

**另一个实测发现**：B 站评论图 URL **会过期**（同一 URL 几分钟后再取可能 404），所以搜到图应尽快发送；
`animatedOnly` 探测失败（含过期）时会自动跳过该张。

**发送通道本身没问题**：HTTP 端点只支持 <2MB 请求体，动图常有 1~4MB，所以发送已全部改走 OneBot WebSocket（见第十节）。

## 十二、修复："引用机器人自己发的图，AI 看不到"

**症状**：用户引用 bot 刚发来的图片问"这是什么"，AI 回答看不到 / 说该消息没有图片。

**根因（三个坑叠加）**：
1. 桥接只把自己发出的**文字**记进上下文（`recordSentMessagesV2` 只写 text），**图片/表情完全没记录**；
2. OneBot 网关配置 `reportSelfMessage: false`，**自消息不会回传**给桥接，所以缓存里根本没有这条；
3. 入站消息只记录 `quoteTargetIsSelf`（布尔），**没有保存被引用消息的 id** —— AI 连"该取哪一条"都不知道。

**修复**：
- 新增 `recordSelfMediaV2()`：机器人发出的图片/表情也会写入 `recentMessages`（带 `messageId` + `media` + `hasMedia`）。
- `fetchOneBotImage()` 支持 `base64://` 直填：网关回读自己发的图时，`file`/`url` 就是 `base64://…`。
- 新增 `fetchMediaFromOneBot(messageId)`：缓存没有（或缓存里的地址已过期/超限）时，用 OneBot `get_msg` 兜底取图片段。
- `/api/images/message` 改成**两级读取**：先查缓存 → 失败再走 `get_msg`。
- 入站解析引用段：记录 `quoteMessageId`，并在消息文本前插入提示
  `[引用你发的图片 messageId=xxx]（要看内容请调用 qq_get_message_images，messageId 传 xxx）`。

**验证**：
```
读改动前发的旧图（缓存里没有） → ok:true, images:1, mimeType:image/gif   ← get_msg 兜底生效
读刚发的 4.19MB 大图（超 URL 抓取上限）→ ok:true, images:1                ← 同样靠兜底
```

**保留的限制**：单张读图仍有体积/像素上限（`MAX_MEDIA_BYTES`）；超出时会返回
`note: 图片元数据存在，但取字节失败（链接可能已过期或超出读图体积上限）`。

## 十五、按需「学梗」：qq_lookup_meme

**背景**：群里大量网络梗。项目原本已有黑话系统（`state/slang.json` 106 条、候选提取、管理端研究），

## 十六、查梗不拖慢回复 + 黑话积压清账

### 16.1 同步路径必须"有预算"

需求原话：**"同步的实现主要还是保证当前的回复速度不受影响。异步的那个还是保留。"**
所以 `qq_lookup_meme` 的同步链路改造成三段，全部有硬预算：

| 顺序 | 数据源 | 耗时 | 超预算时 |
| --- | --- | --- | --- |
| ① | 内存缓存（TTL 10 分钟） | ~1ms | — |
| ② | 本地黑话库（**必须有 `meaning` 才算命中**） | ~1ms | — |
| ③ | B 站视频 + 高赞评论，硬超时 **4000ms** | 实测 ~700ms | 退化为只搜视频标题（再给 2500ms），评论放弃 |

关键修复：
- **候选项不再冒充答案**：原来只要词条存在（哪怕只有 `suggestedMeaning`、`meaning` 为空）就直接返回，
  结果是 AI 拿到一个空释义。现在 `meaning` 为空视为未命中，继续往下走。
- **超时不再报错**：超预算时先返回视频标题（仍然是有效语境），同时把该词排进异步深度考究队列，
  AI 不会因为查梗失败而卡住。
- **缓存与联网返回同样的 JSON 形状**（都包在 `digest` 里），避免调用方写两套解析。
- MCP 客户端超时从 120s 收紧到 **15s**，失败文案明确写"不要重试，直接按上下文回应"——
  查梗只是加分项，卡住回复才是损失。

实测（同一台机器，bridge 本机调用）：
```
「已读乱回」第 1 次（联网）→ 0.70s   from: bilibili  视频 5 / 评论 10
「已读乱回」第 2 次（缓存）→ 0.001s  from: cache     同样的 digest
「哈基米」（已在库）      → ~1ms    from: library   完整释义/用法/例句/风险
```

### 16.2 唤醒提示词里加一句"先查再回"

不改 DSH preset（改 preset 要重启 DSH，会打断会话），改为在 bridge 每次唤醒拼接提示词时
（`withSlangContext`）**总是**注入一小段：

> 【碰到不认识的梗/黑话】先查再回：用 `mcp__snowluma__qq_lookup_meme`（key/token/word）。
> 本地已有释义会立刻返回；没有的话会去 B 站相关视频与高赞评论现学，几秒内出结果…
> 查不到就按上下文自然接话，别硬套术语、也别自己编含义。

这样调整"AI 该不该查梗"的策略不需要重启任何进程，改 `bridge.js` 即可。

### 16.3 异步管线（保留并补上收口）

原有管理端异步研究（`runSlangResearch`）**只写释义、从不改状态**，导致研究出来的词永远停在
`candidate`，而 AI 的 `qq_slang_query` 只认 `confirmed` → 研究了等于白研究。修复：

- 研究结果里 `confirmed: true` 且拿到 `meaning` → **自动转正**为 `confirmed`（`autoConfirmed: true` 留痕），
  由 `slang.autoConfirmResearched`（默认开）控制，关掉即回到人工确认模式。
- `qq_lookup_meme` 写入的候选词条也会排队精研（原来只有 AI 主动 `qq_slang_submit` 才会）。
- 修掉一个顺序 bug：超时分支在词条落库**之前**就调用了入队函数，此时词条还不存在，
  入队被静默忽略；现在统一在落库后入队。

### 16.4 积压清账（`scripts/process-slang-backlog.mjs`）

107 条候选全是 `candidate`，其中只有 5 条有释义、AI 实际上一条都查不到。写了批处理器：

```bash
node scripts/process-slang-backlog.mjs --dry-run          # 只看会删什么、研究会什么
node scripts/process-slang-backlog.mjs --batch=8 --timeout=140000
```

- 只通过控制台 HTTP API 操作（不直接写 `state/slang.json`，避免和 bridge 进程写冲突）。
- **清理只删"明确不是黑话"的类别**：BV 号 / URL / av·cv·uid / 纯数字 / 纯符号 / 超短 ASCII（≤2 字符）/
  十六进制串 / 日期 / 重复项。宁可多留，不可错删 —— 实际只删掉 4 条（`BV19Zeh6YEt2`、`js`、`nb`、`nm`）。
- 其余按 8 条一批 `POST /api/slang/research`，轮询到出释义或超时，再做一次兜底确认。

**结果**：94 条进管线 → **64 条拿到释义并自动转正**（另有 5 条历史释义一并确认）。

```
全库 104 条：confirmed 73，candidate 31
```

剩下 31 条是 B 站查不到依据的群内自造词（`背硬`、`马头牛逼`、`群id`、`菲比丘比`、
`缺啥功能让ai自己做`…）。管线**拒绝瞎编**、保持 `candidate` 是正确行为——
这类只能靠群内语境人工补，或等它们再出现几次后由 AI 带语境提交。

### 16.5 顺手修掉的两个"库一大就废"的问题

1. **`qq_slang_query` 只能看见前 8 条**：`confirmedSlangListV2()` 受 `slang.injectMax`(8) 约束，
   库从 8 涨到 73 后，AI 查"有哪些黑话"永远只拿到 8 条且 `total` 也谎报 8。
   现在列表函数支持显式 `limit`：**注入提示词的短表仍只用 8 条**（控制 prompt 体积与延迟），
   而 AI 主动查询时返回前 60 条 + `confirmedTotal: 73` + "用 q 过滤"的提示；带 `q` 时返回全部匹配。
2. **例：`injectMax` 不动**是有意的——每条释义 300~500 字，把 73 条全塞进每次唤醒的提示词
   会显著增加 token 与延迟，正好违背 16.1 的目标。

## 十七、控制台深色/浅色主题

**需求**：控制台支持切换深色/浅色，**默认浅色**。

**做法**：把 `public/console.html` 里散落的写死色值（原来有 30 个 `#hex`/`rgba()` 直接写在
规则里）全部收进两套变量表，规则只引用 `var(--x)`：

```css
:root { color-scheme: light; --bg: #f4f5f7; --card: #fff; … }   /* 默认浅色 */
:root[data-theme="dark"] { color-scheme: dark; --bg: #0f1115; … } /* 深色覆盖 */
```

- `<html data-theme="light">` 是默认值；**只有明确存过 `dark` 才切深色**，不跟随
  `prefers-color-scheme`（需求要的是"默认浅色"，跟系统走会让浅色用户被系统深色带跑）。
- 深色那一套就是原来控制台本来的配色，**老用户切过去看到的是原来的样子**。
- 切换按钮在右上角标题栏，文案显示的是"点一下会切到哪"（浅色时显示 `🌙 深色`），
  选择存 `localStorage['qq-console-theme']`。
- `color-scheme` 一并切换，让原生滚动条/复选框/下拉也跟着变，不然浅色页面上会挂一条黑滚动条。

**两个容易踩的坑（都已处理）**：

1. **首屏闪一下浅色**：主题必须赶在样式生效前定下来，所以在 `<head>` 里放了一段同步脚本先读
   `localStorage` 打 `data-theme`；放到页面底部就会闪。
2. **浅色下深字压深底**：`.tag.active`、`button.danger` 这类控件原来只有 `background`、
   文字颜色靠继承——深色主题下没问题，浅色主题下会变成深灰字压蓝底/红底。
   现在这类规则显式给 `color: var(--on-accent)`。

**回归测试** `scripts/test-console-theme.mjs`（12 项）锁住四类问题：

```bash
node scripts/test-console-theme.mjs
```

- 结构：两套变量块存在、`<html>` 默认浅色；
- 一致性：两套变量集合完全一致（少定义一个只会静默退化成透明）、规则里**不允许再出现写死色值**、
  `var()` 引用都有定义、有底色的控件必须显式给前景色；
- 行为：用 `node:vm` + 假 DOM 跑真实脚本 —— 无偏好→浅色、存 `dark`→首屏即深色、
  点击来回切且写回 `localStorage`、`localStorage` 被禁（隐私模式）时仍能正常渲染。

**生效方式**：控制台 HTML 是**每次请求现读文件**（`bridge.js` 里 `readFileSync`），
所以改完**刷新页面即可，不用重启 bridge**。
