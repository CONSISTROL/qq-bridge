## 一、P0：工具开关热更新（免重启 DSH）

**问题**：工具表是 MCP 子进程启动时一次性注册的，控制台改开关后模型侧看不到变化，必须重启 DSH。

**改动**（`src/mcp-snowluma-safe.js`）：
- 所有注册统一走 `defineTool()`，拿到 `RegisteredTool` 句柄（支持 `remove/enable/disable`）。
- 注册整体包成 `registerAllTools()`：先 `removeAllTools()`，再按最新 `cfg` 重跑注册。
- `fs.watch(config.json)` + `fs.watchFile`（2s 轮询兜底）+ 300ms 防抖；内容指纹没变则跳过。
- 重注册完只发 **一次** `server.sendToolListChanged()`（批量期间屏蔽逐条通知，否则 36 个工具会打出几十条）。
- DSH 的 `@deepseek-ai/dsh-mcp-client` 本来就监听 `ToolListChangedNotificationSchema` 并会 `re-syncing`，所以**无需重启 DSH**。

**效果**：控制台开关工具 → 1~2 秒内模型工具表同步；DSH 只在**加载这份新代码时**需要重启一次。

**验证**：`node scripts/test-p0-hot-reload.mjs`（隔离副本 `/tmp/mcp-test`，不碰线上配置）
```
✅ 初始工具表包含 qq_get_self_image / qq_save_sticker（36 个）
✅ 关闭开关后工具消失（免重启）   ✅ 收到 list_changed ×1
✅ 重新打开后工具回来（免重启）   ✅ 收到 list_changed ×1
```

## 二、P1：`qq_save_sticker`（把外部图片存进 QQ 收藏表情库）

链路：**桥接自己下载 → 校验 → 转 base64 → 网关 `add_custom_face` → 得到 emoji_id → 之后用现成的 `qq_send_sticker` 发送**。

> 铁律：远程图片一律由桥接 `safeFetchBuffer()` 下载（DNS 固定 + 逐跳重定向校验 + 禁内网 + 格式/体积校验），
> **绝不把原始 URL 交给 OneBot 网关去抓**（那会绕过 SSRF/本地文件防护）。

### 支持的来源
| source | 说明 |
| --- | --- |
| `library`（默认） | `assets/stickers/` 下的**纯文件名**；带路径或 `..` 一律拒绝 |
| `base64` | `data:image/...;base64,...` 或裸 base64；校验确实是 PNG/JPEG/GIF/WebP |
| `url` | http(s) 图片直链；**默认关闭**，需 `socialV2.image.allowRemoteUrl = true`；命中 `refererAllow` 时自动带 Referer（B 站防盗链） |

### 开关与参数
- 工具开关：控制台 **07 二代仿真模式 → 工具开关 → `qq_save_sticker`**（`socialV2.tools.saveSticker`）
- 能力参数（`config.json` → `socialV2.image`）：
```jsonc
"image": {
  "enabled": true,
  "allowRemoteUrl": false,        // 默认只允许本地图库/base64
  "libraryDir": "assets/stickers",
  "maxBytes": 5242880,            // 5MB
  "maxPerMinute": 5,
  "maxPerHour": 30,
  "refererAllow": ["https://www.bilibili.com", "https://b23.tv"]
}
```

### 验证结果（`node scripts/test-p1-save-sticker.mjs`）
```
✅ 拒绝路径穿越            ✅ 图库缺图时报错        ✅ 拒绝非图片文件
✅ 拒绝非图片 base64       ✅ 默认拒绝远程 URL      ✅ 本地图库保存成功（返回 emojiId）
✅ 开启远程后仍拒绝内网地址（SSRF 防护）            ✅ 超过每分钟上限返回 429
```
测试创建的表情已在结束时通过 `delete_custom_face` 删除。

## 三·补：聊天里的图存不进来（2026-09 修复）

**现象**：AI 想把用户/群友发的图收进收藏表情，报「图片站点不在 refererAllow 白名单内」。

**根因**：AI 手上只有消息里的 `media.url`，而那是腾讯自家 CDN
（`https://multimedia.nt.qq.com.cn/download?...&rkey=...`）；当时 `refererAllow` 只列了 B 站图床，
于是每次都被拒。旧实现还有第二个坑：**只要命中白名单就无脑发 `imageReferer`（B 站的 Referer）**，
把它发给腾讯图床反而可能被判盗链。

**修复**（逻辑抽到 `src/image-allow.js`，可离线单测）：

1. 默认与线上 `refererAllow` 补上腾讯/QQ 图片 CDN：
   `multimedia.nt.qq.com.cn` / `multimedia.qpic.cn` / `gchat.qpic.cn` / `c2cpicdw.qpic.cn`。
2. 新增 `refererHosts`（默认 `["hdslb.com","bilibili.com"]`）：**只有列在这里的图床才带 `imageReferer`**，
   其余站点不带 Referer —— 修掉「B 站 Referer 发给腾讯 CDN」的问题。
3. 被拒时的报错**可执行**：QQ CDN 链接会直接提示改用 `qq_collect_sticker(messageId=...)`。
4. 工具描述改口径：**收藏聊天里的图一律用 `qq_collect_sticker`**（走网关取字节，
   不受白名单限制、也不怕 `rkey` 过期）；`qq_save_sticker` 只负责图库 / base64 / 白名单图床。

> 为什么仍然推荐 `qq_collect_sticker`：QQ CDN 链接里的 `rkey` 会过期，
> 而 `qq_collect_sticker` 是用 `get_image` 让网关重新取字节，天然绕开这个问题。
> `refererAllow` 放行腾讯 CDN 只是兜底，不是首选路径。

## 五、P3：B 站抓图入库（`scripts/fetch-bili-images.mjs`）

### 三个图源的无登录可用度（2026-09 实测）
| 来源 | 接口 | 无登录 | 备注 |
| --- | --- | --- | --- |
| 评论区 | `x/v2/reply/wbi/main`（**需 wbi 签名**） | ✅ code=0 | 图在 `data.replies[].content.pictures[].img_src` |
| 动态 | `x/polymer/web-dynamic/v1/opus/feed/space`（wbi） | ✅ 20 条/页 | 每条有 `cover.url`；`opus/detail` 固定 **-352**，要登录 |
| 动态（旧） | `x/polymer/web-dynamic/v1/feed/space` | ❌ 固定 **412** | 风控，需要 cookie |
| 专栏 | `x/article/viewinfo?id=cv` | ✅ | `data.image_urls`；read 页是 JS 渲染，别抓 HTML |
| 视频封面 | `x/web-interface/view?bvid=` | ✅ | `data.pic`（P2 已用它验证发图链路） |

> wbi 签名实现：`nav` 取 `img_url`/`sub_url` → 拼接后按 64 位重排表取前 32 位 mixin key →
> 参数排序 + `wts` + mixin 做 md5 得 `w_rid`。脚本内置，无需第三方库。
> 另外用 `x/frontend/finger/spi` 拿 `buvid3/buvid4` 作 cookie，能显著降低触发风控的概率。

```bash
node scripts/fetch-bili-images.mjs --bvid BV1GJ411x7h7 --cover --comments
node scripts/fetch-bili-images.mjs --mid 946974 --dynamic --dynamic-pages 2
node scripts/fetch-bili-images.mjs --cv 2 --cv 123456
```

## 九、故障复盘：桥接"忙"标记卡死（AI 不回话）

**症状**：日志反复出现 `[reserved2] 会话繁忙，暂存唤醒原因 …`，AI 再也不回话；DSH 侧转录里回合却早已 `turn/end reason=completed`。

**根因**：桥接判断"会话是否忙"靠内存标记（`v2TurnStartAt` / `collectors` / `promptQueues` / `pendingWakeKeys`）。
若**桥接在回合中途重启**，或 **DSH 重启导致终帧丢失**，这些标记会永久残留 → 后续所有唤醒只能排队，永远不投递。

**修复**：新增**忙标记看门狗**（`src/bridge.js`）——
- 排队时记录 `st.pendingSince`；真正放行唤醒时清零
- 每 60s 巡检：某会话排队超过 `socialV2.busyRecoveryMs`（默认 **480000 = 8 分钟**，设 0 关闭）就
  `forceClearBusyV2()` 清掉全部忙标记，并补投一次 `busyRecovery` 唤醒
- 启动日志会打印：`[reserved2] 忙标记看门狗已启动（8 分钟）`

**另外一个坑**：DSH 重启后**不要立刻**让桥接投递（会话可能还在 seeding），否则又会留下脏标记；看门狗现在会自动兜底。

**手动急救**（看门狗生效前/想立刻恢复）：
```bash
cd /home/wx/qq-bridge
# 1) 重启桥接 = 事件流重连会清空忙标记
tmux send-keys -t 1 C-c; sleep 3; tmux send-keys -t 1 'cd /home/wx/qq-bridge && npm start' Enter
# 2) 手动唤醒积压的会话
curl -s -X POST "http://127.0.0.1:3100/api/socialV2/wake?token=$(cat state/console-token)" \
  -H 'content-type: application/json' -d '{"key":"private:10001","reason":"admin"}'
```

**会话上下文太脏时**（例如它一直重发旧的视频封面 URL）：删掉该 key 的 DSH 会话映射，下次唤醒会新建干净会话。

与图片搜索/发送无关；同一路径手动下载验证正常。需要的话可给 sticker 发送加一次重试。

## 十、故障复盘：大图发送失败（fetch failed / UND_ERR_SOCKET）

**症状**：`qq_send_image` / `qq_send_sticker` 偶发 `发送图片失败：fetch failed`；日志里 `工具发送表情失败 … fetch failed`。

**实测定位**：

| 路径 | 1MB body | 2MB body | 3.3MB body |
| --- | --- | --- | --- |
| 宿主 → `127.0.0.1:3000`（经 docker-proxy） | ✅ | ❌ `UND_ERR_SOCKET` | ❌ |
| 宿主 → 容器 IP `172.18.0.2:3000`（绕过 proxy） | — | — | ❌ `ECONNRESET` |
| **桥接 → OneBot WebSocket（3001）** | ✅ | ✅ | ✅ **成功** |

**结论**：**不是 docker-proxy**，是 SnowLuma 的 **HTTP 端点在请求体 ≥2MB 时会直接断连**。
而 base64 图片动辄 3~7MB（2.4MB 的 PNG → 3.1MB base64），所以大图必挂；小表情偶尔挂是同一原因的边缘抖动。

**修复**（`src/bridge.js`）：新增统一的 `postOneBot(action, params)`，
**优先走 OneBot WebSocket**（收藏表情的 base64 本来就一直走 WS，稳定），失败才回退 HTTP 并重试（300ms/900ms 指数退避）；
错误信息带底层 `cause.code` 便于定位。文字、图片、表情三条发送路径全部改走它。

**验证**：
```
send-image 发 2.4MB 评论图 → ok:true，messageId=-585133311（WS 返回结构已归一化）
让 AI 自己跑一轮 → 2 张评论图 + 1 个收藏表情 + 2 条文字，全部成功；WS 回退次数 = 0
```

> 若想更保守，可把 `socialV2.image.maxBytes` 从 5MB 降到 3MB；走 WS 后基本不需要。

## 十一、"GIF 发出来不动"的真相

**不是发送通道的问题，是图本身不是动图。**

诊断过程：
1. 精确解析用户看到的那张 `.gif`（B 站评论区图）：**`GIF89a`，300x323，帧数 = 1，总时长 0.0s，无循环标记** → 它就是个**单帧静态 GIF**。
2. 对比实测：B 站"大肥鱼 动图"搜索里，`.gif` 中确有 106 帧 / 32 帧 / 59 帧的真动图；也有 1 帧的静态图。**B 站评论区/专栏大量 `.gif` 是视频帧导出的静态图**。
3. 之前那个"128 帧"是我粗略数 `0x2C` 字节的误判（LZW 数据里也会出现该字节）。

**修复**：
- 新增 `src/image-meta.js`：按 GIF 块结构精确解析帧数（`gifFrameCount` / `isAnimatedWebp` / `describeAnimation`）。
- `qq_search_images` 新增参数 **`animatedOnly`**：逐张下载探测帧数，只返回真动图（实测把 6 张过滤成 2 张真动图）。
- `qq_send_image` / `qq_save_sticker` 的返回里带上 `animated` / `frames`；发到单帧静态 `.gif` 时桥接日志会提示
  `[image] 注意：… 是单帧静态 .gif（不会动）`。
- MCP 工具描述里也加了提醒：需要动图请传 `animatedOnly: true`。

**另一个实测发现**：B 站评论图 URL **会过期**（同一 URL 几分钟后再取可能 404），所以搜到图应尽快发送；
`animatedOnly` 探测失败（含过期）时会自动跳过该张。

**发送通道本身没问题**：HTTP 端点只支持 <2MB 请求体，动图常有 1~4MB，所以发送已全部改走 OneBot WebSocket（见第十节）。

## 十二、修复："引用机器人自己发的图，AI 看不到"

**症状**：用户引用 bot 刚发来的图片问"这是什么"，AI 回答看不到 / 说该消息没有图片。

**根因（三个坑叠加）**：
1. 桥接只把自己发出的**文字**记进上下文（`recordSentMessagesV2` 只写 text），**图片/表情完全没记录**；
2. OneBot 网关配置 `reportSelfMessage: false`，**自消息不会回传**给桥接，所以缓存里根本没有这条；
3. 入站消息只记录 `quoteTargetIsSelf`（布尔），**没有保存被引用消息的 id** —— AI 连"该取哪一条"都不知道。

**修复**：
- 新增 `recordSelfMediaV2()`：机器人发出的图片/表情也会写入 `recentMessages`（带 `messageId` + `media` + `hasMedia`）。
- `fetchOneBotImage()` 支持 `base64://` 直填：网关回读自己发的图时，`file`/`url` 就是 `base64://…`。
- 新增 `fetchMediaFromOneBot(messageId)`：缓存没有（或缓存里的地址已过期/超限）时，用 OneBot `get_msg` 兜底取图片段。
- `/api/images/message` 改成**两级读取**：先查缓存 → 失败再走 `get_msg`。
- 入站解析引用段：记录 `quoteMessageId`，并在消息文本前插入提示
  `[引用你发的图片 messageId=xxx]（要看内容请调用 qq_get_message_images，messageId 传 xxx）`。

**验证**：
```
读改动前发的旧图（缓存里没有） → ok:true, images:1, mimeType:image/gif   ← get_msg 兜底生效
读刚发的 4.19MB 大图（超 URL 抓取上限）→ ok:true, images:1                ← 同样靠兜底
```

**保留的限制**：单张读图仍有体积/像素上限（`MAX_MEDIA_BYTES`）；超出时会返回
`note: 图片元数据存在，但取字节失败（链接可能已过期或超出读图体积上限）`。

## 十六、查梗不拖慢回复 + 黑话积压清账

### 16.1 同步路径必须"有预算"

需求原话：**"同步的实现主要还是保证当前的回复速度不受影响。异步的那个还是保留。"**
所以 `qq_lookup_meme` 的同步链路改造成三段，全部有硬预算：

| 顺序 | 数据源 | 耗时 | 超预算时 |
| --- | --- | --- | --- |
| ① | 内存缓存（TTL 10 分钟） | ~1ms | — |
| ② | 本地黑话库（**必须有 `meaning` 才算命中**） | ~1ms | — |
| ③ | B 站视频 + 高赞评论，硬超时 **4000ms** | 实测 ~700ms | 退化为只搜视频标题（再给 2500ms），评论放弃 |

关键修复：
- **候选项不再冒充答案**：原来只要词条存在（哪怕只有 `suggestedMeaning`、`meaning` 为空）就直接返回，
  结果是 AI 拿到一个空释义。现在 `meaning` 为空视为未命中，继续往下走。
- **超时不再报错**：超预算时先返回视频标题（仍然是有效语境），同时把该词排进异步深度考究队列，
  AI 不会因为查梗失败而卡住。
- **缓存与联网返回同样的 JSON 形状**（都包在 `digest` 里），避免调用方写两套解析。
- MCP 客户端超时从 120s 收紧到 **15s**，失败文案明确写"不要重试，直接按上下文回应"——
  查梗只是加分项，卡住回复才是损失。

实测（同一台机器，bridge 本机调用）：
```
「已读乱回」第 1 次（联网）→ 0.70s   from: bilibili  视频 5 / 评论 10
「已读乱回」第 2 次（缓存）→ 0.001s  from: cache     同样的 digest
「哈基米」（已在库）      → ~1ms    from: library   完整释义/用法/例句/风险
```

### 16.2 唤醒提示词里加一句"先查再回"

不改 DSH preset（改 preset 要重启 DSH，会打断会话），改为在 bridge 每次唤醒拼接提示词时
（`withSlangContext`）**总是**注入一小段：

> 【碰到不认识的梗/黑话】先查再回：用 `mcp__snowluma__qq_lookup_meme`（key/token/word）。
> 本地已有释义会立刻返回；没有的话会去 B 站相关视频与高赞评论现学，几秒内出结果…
> 查不到就按上下文自然接话，别硬套术语、也别自己编含义。

这样调整"AI 该不该查梗"的策略不需要重启任何进程，改 `bridge.js` 即可。

### 16.3 异步管线（保留并补上收口）

原有管理端异步研究（`runSlangResearch`）**只写释义、从不改状态**，导致研究出来的词永远停在
`candidate`，而 AI 的 `qq_slang_query` 只认 `confirmed` → 研究了等于白研究。修复：

- 研究结果里 `confirmed: true` 且拿到 `meaning` → 可自动转正为 `confirmed`（`autoConfirmed: true` 留痕），
  由 `slang.autoConfirmResearched` 控制。**上线 RAG 后默认改为 `false`**：语义检索会主动高频召回，
  LLM 编错的释义会被推到相关对话里，所以保留人工闸门——研究完停在候选，控制台点确认才可用。
  （`scripts/process-slang-backlog.mjs` 也已同步：默认只研究不确认，加 `--confirm` 才代为确认。）
- `qq_lookup_meme` 写入的候选词条也会排队精研（原来只有 AI 主动 `qq_slang_submit` 才会）。
- 修掉一个顺序 bug：超时分支在词条落库**之前**就调用了入队函数，此时词条还不存在，
  入队被静默忽略；现在统一在落库后入队。

### 16.4 积压清账（`scripts/process-slang-backlog.mjs`）

107 条候选全是 `candidate`，其中只有 5 条有释义、AI 实际上一条都查不到。写了批处理器：

```bash
node scripts/process-slang-backlog.mjs --dry-run          # 只看会删什么、研究会什么
node scripts/process-slang-backlog.mjs --batch=8 --timeout=140000
```

- 只通过控制台 HTTP API 操作（不直接写 `state/slang.json`，避免和 bridge 进程写冲突）。
- **清理只删"明确不是黑话"的类别**：BV 号 / URL / av·cv·uid / 纯数字 / 纯符号 / 超短 ASCII（≤2 字符）/
  十六进制串 / 日期 / 重复项。宁可多留，不可错删 —— 实际只删掉 4 条（`BV19Zeh6YEt2`、`js`、`nb`、`nm`）。
- 其余按 8 条一批 `POST /api/slang/research`，轮询到出释义或超时，再做一次兜底确认。

**结果**：94 条进管线 → **64 条拿到释义并自动转正**（另有 5 条历史释义一并确认）。

```
全库 104 条：confirmed 73，candidate 31
```

剩下 31 条是 B 站查不到依据的群内自造词（`背硬`、`马头牛逼`、`群id`、`菲比丘比`、
`缺啥功能让ai自己做`…）。管线**拒绝瞎编**、保持 `candidate` 是正确行为——
这类只能靠群内语境人工补，或等它们再出现几次后由 AI 带语境提交。

### 16.5 顺手修掉的两个"库一大就废"的问题

1. **`qq_slang_query` 只能看见前 8 条**：`confirmedSlangListV2()` 受 `slang.injectMax`(8) 约束，
   库从 8 涨到 73 后，AI 查"有哪些黑话"永远只拿到 8 条且 `total` 也谎报 8。
   现在列表函数支持显式 `limit`：**注入提示词的短表仍只用 8 条**（控制 prompt 体积与延迟），
   而 AI 主动查询时返回前 60 条 + `confirmedTotal: 73` + "用 q 过滤"的提示；带 `q` 时返回全部匹配。
2. **例：`injectMax` 不动**是有意的——每条释义 300~500 字，把 73 条全塞进每次唤醒的提示词
   会显著增加 token 与延迟，正好违背 16.1 的目标。

## 十七、控制台深色/浅色主题

**需求**：控制台支持切换深色/浅色，**默认浅色**。

**做法**：把 `public/console.html` 里散落的写死色值（原来有 30 个 `#hex`/`rgba()` 直接写在
规则里）全部收进两套变量表，规则只引用 `var(--x)`：

```css
:root { color-scheme: light; --bg: #f4f5f7; --card: #fff; … }   /* 默认浅色 */
:root[data-theme="dark"] { color-scheme: dark; --bg: #0f1115; … } /* 深色覆盖 */
```

- `<html data-theme="light">` 是默认值；**只有明确存过 `dark` 才切深色**，不跟随
  `prefers-color-scheme`（需求要的是"默认浅色"，跟系统走会让浅色用户被系统深色带跑）。
- 深色那一套就是原来控制台本来的配色，**老用户切过去看到的是原来的样子**。
- 切换按钮在右上角标题栏，文案显示的是"点一下会切到哪"（浅色时显示 `🌙 深色`），
  选择存 `localStorage['qq-console-theme']`。
- `color-scheme` 一并切换，让原生滚动条/复选框/下拉也跟着变，不然浅色页面上会挂一条黑滚动条。

**两个容易踩的坑（都已处理）**：

1. **首屏闪一下浅色**：主题必须赶在样式生效前定下来，所以在 `<head>` 里放了一段同步脚本先读
   `localStorage` 打 `data-theme`；放到页面底部就会闪。
2. **浅色下深字压深底**：`.tag.active`、`button.danger` 这类控件原来只有 `background`、
   文字颜色靠继承——深色主题下没问题，浅色主题下会变成深灰字压蓝底/红底。
   现在这类规则显式给 `color: var(--on-accent)`。

**回归测试** `scripts/test-console-theme.mjs`（12 项）锁住四类问题：

```bash
node scripts/test-console-theme.mjs
```

- 结构：两套变量块存在、`<html>` 默认浅色；
- 一致性：两套变量集合完全一致（少定义一个只会静默退化成透明）、规则里**不允许再出现写死色值**、
  `var()` 引用都有定义、有底色的控件必须显式给前景色；
- 行为：用 `node:vm` + 假 DOM 跑真实脚本 —— 无偏好→浅色、存 `dark`→首屏即深色、
  点击来回切且写回 `localStorage`、`localStorage` 被禁（隐私模式）时仍能正常渲染。

**生效方式**：控制台 HTML 是**每次请求现读文件**（`bridge.js` 里 `readFileSync`），
所以改完**刷新页面即可，不用重启 bridge**。

## 十八、本地向量检索（RAG）：黑话选词从「固定 8 条」改为「按当前消息选」

### 18.1 为什么非做不可

原来 `buildSlangContext` 按 `count` 降序取 8 条注入。但库里 **68/73 条的 `count` 都是 1**，
对 93% 取值相同的字段排序等于没排，结果是**这 8 条被永久冻死**：

```
永远注入：炫狗、blg bin、电击小子、欧金金、涩图、ig theshy、量子速读、恒生科技
其余 65 条：永远不会出现在任何一次唤醒提示词里
```

而且它**与查询无关**——任何群、任何一句话都注入同样 8 条。加上 `evidence[].key` 里
明明有会话归属（58/73 条来自 `group:1050666134`），另一个群拿到的是 79% 隔壁群的词汇。

### 18.2 评测：先有数字，再谈优化

评测集直接用 `evidence[].text` 里的真实群消息，零额外标注成本。

| 评测集 | 基线（固定 top-8） | 词法（子串匹配） | 向量 |
| --- | --- | --- | --- |
| A：76 条真实消息（**字面命中**） | **15.8%** | ~100% | **100%** |
| B：14 条手写**非字面**查询（消息里不含目标词） | **0/14** | **0/14** | **14/14** |

**关键在 B 集**：A 集全部是字面命中，向量赢的只是「vs 按频次排序」，词法同样能到 100%。
B 集才是向量的不可替代价值——目标词根本没出现在消息里：

```
「他名字念起来像日语里那个下流的词」        → 欧金金
「翻书翻得飞快，等于没看」                  → 量子速读
「短期均线穿过长期均线了，是买点吗」        → 金叉
「阴阳怪气地夸人，满嘴跑火」                → 小嘴抹了蜜 / 嘴欠型
「只有机器人管理员才有权限开这个」          → owner / 群主
```

> B 集只有 14 条且是我手写的（知道库里有什么），存在选择偏差，只作方向性参考。
> 但 14/14 对 0/14 的对比，足以说明语义检索解决的是词法**原理上**解决不了的问题。

### 18.3 成本：全部实测（这台 2U2G / 可用内存 488MB）

| 指标 | 实测值 |
| --- | --- |
| 模型文件（bge-small-zh-v1.5 int8） | 22.9 MB |
| 依赖磁盘（onnxruntime-node，自带 linux 二进制） | ~240 MB |
| 冷启动（加载 + 首次编码） | 212 ms |
| 单条 query 编码（常驻预热后） | **6.9 ms**（P95 7.7ms） |
| 全库 73 条编码（batch=8） | 2.78 s（38ms/条） |
| 常驻内存峰值 | **176~190 MB** |
| 全库重建峰值 | **227 MB** |
| 向量存储 73×512 维 | 310 KB |

**两条实测出来的硬约束**：

1. **批量必须小**：一次性把 104 条丢进去会在注意力张量上**被 OOM 杀掉**（退出码 137）。
   8 条一批 + 截断 256 tokens 后峰值稳定在 227MB。代码里 `batch=8` 是硬性的。
2. **别信估算**：我先前估「int8 权重 25MB + 运行时 ≈ 80MB」，实测 176~227MB，**低估约 3 倍**。
   ONNX Runtime 自身开销远大于量化权重。

### 18.4 架构：三条「绝不影响主流程」的隔离

```
QQ 消息 → bridge (withSlangContext, async)
            ↓ 编码当前消息（超时 1.5s，典型 7ms）
            ↓ 余弦 + 会话维度 + 时间衰减 → 选 top-K
            ↓ 失败/超时/不可用 → 退回 buildSlangContext（按出现次数）
          src/embedding-client.js  ← stdio JSON →
          src/embedder.js（独立子进程，常驻 ~190MB，崩了自动退避重启）
```

- **进程隔离**：模型跑在独立子进程，才能用 cgroup 套硬限额；OOM 也只死它自己。
  用 `config.rag.spawnPrefix` 给子进程加内存闸门，本机已启用：

```json
"spawnPrefix": "systemd-run --scope -p MemoryMax=320M -p MemorySwapMax=0 --quiet"
```

  实测可用（bridge 作为父进程启动 systemd-run 正常）。**必须带 `--quiet`**，
  否则 systemd-run 会往 stdout 打一行 "Running as unit: …"，污染 stdio JSON 协议。
  清空该字段即关闭。失败时控制台 08b 面板会显示「已启用但子进程不可用」。
- **依赖隔离**：`@xenova/transformers` 放在 `optionalDependencies`，缺了不影响主程序启动。
- **失败降级**：任何一步出错都退回历史行为，行为**不退化**（只是不再智能选词）。

新增/改动文件：

| 文件 | 作用 |
| --- | --- |
| `src/embedder.js` | 本地 embedding 子进程（stdio 协议，批≤8、截断 256） |
| `src/embedding-client.js` | 客户端：超时、自动重启、退避、内存上报 |
| `src/slang-index.js` | 向量库、重建计划、打分、选词、近义聚类 |
| `src/slang-learner.js` | `normalizeSlangEntry` 增加 `aliases`/`tags`；抽出 `formatSlangTable` |
| `src/bridge.js` | `withSlangContext` 改异步+query-aware；4 个控制台路由；查梗向量兜底 |
| `public/console.html` | RAG 面板：状态 / 重建 / 检索调试 / 近义聚类 |
| `scripts/fetch-embed-model.mjs` | 从 **ModelScope** 拉模型（HuggingFace 在本机不可达） |
| `scripts/eval-slang-retrieval.mjs` | 基线 vs 向量评测（A/B 两个评测集） |
| `scripts/test-rag-retrieval.mjs` | 18 项回归测试（离线逻辑 + 在线端到端） |

`loadSlang` 每次加载都跑 `normalizeSlangEntry`，新字段在加载时自动回填，**不需要迁移脚本**。

### 18.5 参数是实测校准出来的，不是拍的

`minCosine` 我一开始按「手挑 7 对样本」估成 **0.32**（那 7 对显示相关 ≥0.55、无关 ≤0.31）。
但调试面板一上线就打脸：一条查询 `eligible=63/73`，除第 1 名(0.545)外全是 0.42~0.46 的噪声——
**在全库规模上无关对能到 0.50**，那 7 对样本的「干净空隙」不成立。

修正两处：

1. `minCosine` 提到 **0.5**（贴着相关下沿）。调紧后 A 集仍 100%、B 集仍 14/14，**召回没掉**，
   说明被挡掉的确实是噪声。
2. 加**相对判据** `relativeMargin=0.08`：只保留离 top-1 不超过这个距离的条目。
   因为 0.50~0.57 这一段仍然密集（「评价一下blg bin」top-1 是 0.75，后面全在 0.50~0.52），
   单纯调高绝对阈值会误伤。

另外把「会话维度」从**资格豁免**改成**只参与打分**：早先让 `conv>0` 直接获得资格，
结果本库 58/73 条都出现过的词几乎全都能进，等于把噪声放了进来。群内自造词（余弦天然偏低）
改由 `minFill` 兜底带出。

改完的效果：

```
「被笔记本外壳电了一下，麻了」→ eligible=1，精准命中 电击小子(0.55) + 2 条本群高频补位
「评价一下blg bin」          → eligible=8，top-1 blg bin(0.75)
```

### 18.6 控制台面板（08b）

- **状态**：模型/维度/已索引/待补/孤儿/构建时间/embedder 内存/累计编码次数与均值
- **检索调试**：输入一句话，**并排显示旧（按频次）与新（按语义）各自会注入什么**，
  附 `sem/conv/score` 分解 + 「差一点没进」列表。这是判断 RAG 有没有用的唯一手段，
  也是调 `minCosine`/`relativeMargin`/`topK` 的依据。
- **近义聚类**：按余弦列出词条对，人工决定合并 / 建别名 / 忽略。实测头部结果：
  `难绷~没绷住 0.953`、`涩图~色图 0.908`、`没绷住~蚌埠住了 0.902`、`owner~群主 0.805`——
  这些重复确实存在，人工审核比写死规则靠谱。

### 18.7 部署注意

- **`sharp` 的坑**：`@xenova/transformers` 在**模块加载时**就 `require('sharp')`，
  而它依赖的 `sharp@0.32` 原生二进制要从 **GitHub releases** 下载（本机超时 → 装不上）。
  文本编码根本用不到 sharp。解法是 `package.json` 里 `overrides: { "sharp": "^0.33.5" }`——
  0.33+ 改走 `@img/sharp-linux-x64` 这个 **npm 包**分发二进制，不碰 GitHub。
- **内存**：常驻约 190MB（cgroup 口径 123MB）。这机器有 **3 次 OOM 史**且已在吃 swap，
  所以给 embedder 子进程加了 `MemoryMax=320M`（见 18.4，实测超限会被 SIGKILL，退出码 137，
  不会拖累整机）。
- **但内存不是凭空来的**：上线后实测 `free` 的 used/available 几乎没变（1121MB/491MB），
  而 **swap 从 1352MB 涨到 1708MB（+356MB）**——也就是说这 123~190MB 主要是把别的进程的页
  挤进了 swap，代价是那些进程被访问时变慢。这是「2G 机器上多加一个常驻服务」的真实成本，
  不是 RAG 特有的问题，但它确实是新增的那一份压力。
  如果 swap 压力变成问题，可选的退路是**不常驻**：冷启动实测 212ms/次、
  常驻内存 0，对「DeepSeek 生成本来就要几秒」的场景可以接受。
- **模型不入库**：`models/` 已加进 `.gitignore`；换机器跑 `node scripts/fetch-embed-model.mjs`。
- **不重启 DSH**：提示词由 bridge 侧拼装，改选词策略只重启 bridge。

## 十九、任务分级：复杂任务可以多花时间，但硬上限不可突破

### 19.1 需求

「复杂任务要让 AI 识别出来，可以多花些时间处理，回答可以长一些」——
但**不能突破硬上限**。

### 19.2 原来的三层限制（都实测过）

| 层 | 位置 | 原值 | 后果 |
| --- | --- | --- | --- |
| 提示词·条数 | preset 规则 16 | 普通对话最多 **2 条**，「2 条封顶」 | 分析类回答被压成一句敷衍 |
| 提示词·长度 | preset 搜索段 | 「仍要简洁」 | 查完资料也只能写一句 |
| 代码·条数 | `socialV2.send.burstMaxMessages` | **8** | 超过直接 400 |
| 代码·长度 | `socialV2.send.maxMessageChars` | 500 | 超过直接 400 |
| 代码·频率 | `maxSendPerMinute / maxSendPerHour` | **8 / 60** | 长回答发到第 9 条撞 429 |
| 代码·劝阻 | `burstHint` | 硬编码 `>=3` 条就提示「真人很少一口气补完」 | 等于否定「可以长」 |

注意第 5 行：**光放开条数不够**——一个 20 条的回复会先撞上「每分钟 8 条」。这三者是叠加的。

### 19.3 改法：分层放开，但留死天花板

**代码层（硬上限，超了直接拒绝，不是截断）**

```json
"send": {
  "burstMaxMessages": 24,        // 8 → 24
  "maxSendPerMinute": 30,        // 8 → 30
  "maxSendPerHour": 300,         // 60 → 300
  "maxMessageChars": 500,        // 不动：单条再长就没人读了，长内容应该分条
  "burstHintThreshold": 10       // 原为硬编码 3
}
```

`burstHint` 的文案也改了：原来无条件说「真人很少一口气补完」，
现在明确把正经事排除在外（「如果这是在回答分析/资料/正经问题，忽略这条提示」）。

**提示词层（让 AI 自己分级，且知道天花板在哪）**

bridge 每次唤醒注入（不依赖 preset，改完立即生效）：

```
【先分清是闲聊还是正经事，这决定你花多少力气】
闲聊/接梗/斗嘴：1~3 条、短句，别端着，别写小作文。
正经事（分析、对比、查资料给结论、写东西、算账、debug）：条数可以放宽——
可以先做多步检索（搜索→打开正文→换关键词交叉验证）再回，可以花几分钟，
可以写长、分多条把一件事讲清楚。宁可多花时间给一个有依据的答案，也不要为了显得随意而敷衍一句。
但硬上限必须遵守：一次最多 24 条、单条最多 500 字，
超了会被直接拒绝（不是截断），所以要主动分批或精简，别撞上去。
过程中不必向群里汇报进度，做完再回。
```

**上限数字是从配置里读出来写进提示词的**，不是硬编码在文案里——
这样它两个作用都达到了：知道可以写长，也知道天花板的确切位置，
不会去撞 400/429 再白费一轮。

预设里同步加了规则：`【硬上限不可突破】…超了会被桥接直接拒绝（不是帮你截断），
所以要主动分批或精简`，并删掉了原来「不受条数限制」的说法。

**可回退**：`socialV2.taskTriage = false` 即关闭这段注入，回到纯 preset 行为。

### 19.4 验证（真的拦得住，且拦下时不会发出去半条）

```
发 25 条        → {"ok": false, "error": "最多发送 24 条"}
单条 501 字     → {"ok": false, "error": "单条消息不能超过 500 字"}
不带 agent token → {"ok": false, "error": "reserved2 模式发送必须携带 agent token"}
日志里的真实发送记录：0 条
```

上限检查在 `sendMessagesV2` **之前**执行，所以被拒时**一条都不会发出去**。

### 19.5 事故与运维发现（都值得记）

**① 我从 16:08 起的所有「重启 bridge」其实都失败了。**
症状：改完配置重启，`/api/socialV2/config` 返回的还是旧值。
原因：当时跑着的是**另一个会话在 16:08 启动的、脱离 tmux 的孤儿 bridge**（`ppid=1`），
它占着 3100；而 `state/bridge.lock` 里写着它的 pid，新实例一启动就报
「已有实例在运行」然后退出。我在 tmux 里 `C-c` 杀的是**一个早就不存在的前台进程**，
看上去"重启成功"（pane 里有启动日志，其实是历史回滚缓冲），实际什么都没换掉。

排查方法：`ps -o lstart` 看进程启动时间 vs 配置文件 mtime；`ss -ltnp | grep 3100` 看**是谁**占着端口；
`cat state/bridge.lock` 看锁里记的 pid 是否还活着。

正确做法：`kill -TERM <占端口的pid>`（锁会自动清除、embedder 子进程会随父进程 stdin EOF 自己退出，
实测无残留），再在 tmux 里 `npm start`。

**② 我又把 preset 的 YAML 改坏了一次。**
用 python 做字符串替换时，替换文本里带了换行却没缩进，
把 YAML 块标量（`prefix: >-`）截断了——`'先给结论…'` 落在了第 0 列。
而且我当时**已经把它同步到了运行时副本** `/root/.dsh/.agent-presets/qq-chat-v2/`，
一旦 DSH 为新会话加载这个 preset 就会失败。

处理：立刻从 `/tmp/preset-v2.bak-tasktriage` 恢复两份，
然后重做时**每一步替换后都跑一次 js-yaml 校验，通过才写下一处、最后才同步运行时副本**。
最终 33115 字节，两份一致，YAML 合法。

**教训（和前两次同类）**：动 `config.json` / preset 这类"改了就可能让系统起不来"的文件，
必须先备份、每步校验、确认无误再推给运行时；不要做"改完一起检查"。

## 二十、B站视频理解：AI 能「听懂」也能「看见」B站视频

### 20.1 结论先行（全部实测）

| 能力 | 来源 | 实测可得率 | 成本 |
| --- | --- | --- | --- |
| **字幕文字稿**（视频里实际说的话） | B站 AI 字幕 | 5/8 视频 | 49 分钟 ≈ 6,700 字 ≈ **4,710 token** |
| **画面**（按时间点取帧） | B站进度条预览雪碧图 | **8/8 视频** | 600 帧共约 **6MB**；但视觉 token 贵，只看几帧 |

两者**互补**：画面 8/8、字幕 5/8。没字幕的（集锦、完整版回放）靠画面补。

### 20.2 为什么这条路这么省：B站自己把活干了

```
不需要下载视频（几百 MB）  → 雪碧图 6 张共约 6MB
不需要装 ffmpeg            → 帧已经是 B站 抽好的
不需要语音识别 ASR         → B站 已经生成 AI 字幕，直接给文字
```

`x/player/videoshot` 返回 6 张雪碧图 × 10×10 = 600 帧、每帧 **480×270**、带 589 个时间戳、覆盖全片（约每 5 秒一帧）。用 `sharp` 按网格切开即可。

`x/player/wbi/v2` 返回字幕列表 → 取 `subtitle_url` → JSON 正文 `body[{from,to,content}]`。

### 20.3 实测看到的画面

取第 1455s / 1470s 两帧，能清楚分辨：**游戏内时间（16:16 → 27:16）、双方比分、阵容英雄头像、主播分镜**，第一帧甚至有烧进画面的字幕「当时好像有人说了先锋还有40秒」。

所以「看画面」是真的能看，不只是拿到一张图。

### 20.4 踩到的三个坑（都写进代码了）

**① 字幕 URL 必须用 wbi 版接口。**
`x/player/v2` 和 `x/player/wbi/v2` 都会返回 `subtitle_url`，但**前者的 URL 是过期的**（实测两版 URL 不同，用旧的那个取不到内容）。必须用 wbi 版。

**② `videoshot` 约 1/4 概率不返回 `index` 时间戳数组。**
`image`（6 张图）正常返回，但 `index` 是空数组——没有时间戳就选不出任何帧，表现为「取帧返回 0 张、且没有报错」，很难查。
处理：先**重试一次**（多数第二次就有了）；仍为空则**按 B站固定的 5 秒采样合成时间戳**，帧数上限取 `floor(时长/5)+1`（2937 秒的视频正好得到 589，与实测一致），并标记 `indexSynthesized` 说明是估算值。

**③ 我一上来写了个不存在的函数。**
路由里写了 `if (!v2Enabled() || ...)`，但 `v2Enabled` 在 bridge.js 里**根本没有定义**——首次调用就会 ReferenceError。改用项目实际的 `cfg.socialV2?.enabled === false`，并加了一段脚本扫描全文件「调用了但没定义的函数」来兜底。

### 20.5 新增的三个工具

| 工具 | 作用 |
| --- | --- |
| `qq_video(word? \| bvid?, offset?, limit?)` | 二合一：给 `word` **搜视频**（返回 bvid 列表）；给 `bvid` **读字幕文字稿**（+ 元数据 + 字数/token 估算）。两个都传或都不传会返回明确提示 |
| `qq_video_frames(bvid, atSeconds, count?, spreadSeconds?)` | 取该时刻附近几帧，**图像直接进模型上下文** |

**为什么只合了前两个、留着 frames 单独一个**（这是权衡后的决定，不是偷懒）：

1. **返回类型不同**：前两个返回文本 JSON，frames 返回**图像 content**。硬合一个要按 `action` 条件返回两种 content 类型。
2. **代价差一个数量级**：搜索约 1 秒；读字幕 2 次 API；取帧要下 1.5MB 雪碧图 + `sharp` 切图 + 几百 KB base64 出去。误触发取帧**一帧白烧约 1000 token**。
3. **参数适用性割裂**：`word` 只对搜索有意义，`atSeconds/count/spreadSeconds` 只对取帧有意义。合成一个工具，AI 得同时选对 action **和**配套参数——这是 malformed call 的主要来源。
4. **项目已有先例**：`qq_get_message_detail`（文本）与 `qq_get_message_images`（图像）就是按返回类型分开的。

**顺带量到了一个更值得注意的数字**：所有工具 schema 合计约 **2 万 token**，每次请求都要带上（占 128K 上下文的 16%）。我加的这组只占 6.3%，而**表情组 9 个工具占 20.8%**——真要省上下文，收益在那边。

路由：`/api/socialV2/bili-video`（search/info/subtitle）、`/api/socialV2/bili-frames`（返回 base64 图像）。
开关：`socialV2.tools.videoSearch / videoTranscript / videoFrames`；总开关 `bili.enabled`。

**正确用法是「字幕定位 + 画面确认」**：两者时间戳对齐——字幕告诉你「第 32 分钟他说 BP 被压了」，再去取 32 分钟附近的帧看当时的 BP 画面。**绝不能扫全片**（600 帧 ≈ 60 万 token）。这条已经写进 `qq_video_frames` 的工具描述里。

### 20.6 限制（诚实说）

1. **AI 字幕有识别错误**，人名/英雄名经常错——实测「安蓓萨」被写成「安萨」、「我们阿里马四对三」这类乱码。**总结观点可以，引用具体名词要存疑**。这条也写进了工具描述。
2. **画面只有 480×270**，看得清 HUD 数字/阵容/大致场面，看不清小字和瞬时操作。
3. **约每 5 秒一帧**，团战可能正好被错过。
4. **看画面 ≠ 看懂比赛**：能看到"这波团战发生在下路河道"，看不出"这波为什么输"——那要靠字幕里的解说。
5. **视觉 token 是真实成本**，必须按需取帧。

## 二十一、pixiv 找图 + 图片年龄分级

### 21.1 结论先行

- **pixiv 直连不通**：`www.pixiv.net` / `i.pximg.net` / `app-api.pixiv.net` 在这台机器上 DNS 被污染（解析到 `2a03:2880:...` 这类假地址），用真实 IP 硬指也超时；1.1.1.1 的 DoH 被拦，本机没有任何代理。所以"AI 能不能上 pixiv"的答案一直是**不能**。
- **能用的两条路**（都实测过）：
  1. `bobopic.com` 镜像了 pixiv 的**综合日榜**和**中文标签页**，能拿到作品 id、标签、标题、分辨率；
  2. `pixiv.re` 按作品 id 代理原图，`https://pixiv.re/<id>.png`。
  于是"找图" = 在 bobopic 上按关键词/日榜拿 id，"发图" = 拼 pixiv.re 直链交给 `qq_send_image`。
- **不用给 bot 开本地工具**：`mcp__web-search-safe__web_fetch` 本来就能读到 bobopic 页面，现在只是把这条路径产品化成一个工具参数。

### 21.2 `qq_search_images` 长了第二个来源

```
source=auto       # 默认（MCP 侧）：先按中文标签试 pixiv，少于 3 张就自动补 B 站
source=bilibili  # 梗图/表情包，取相关视频评论区
source=pixiv     # 二次元插画/角色图；query 用中文标签；mode=daily 取综合日榜（query 可省）
source=all       # 两边都搜
```

- pixiv 项的字段：`id` / `url`（pixiv.re 原图）/ `thumbUrl`（`img.pixivdaily.com/small/<id>.jpg`，几十 KB）/ `title` / `tags` / `width` / `height` / `rating` / `detailUrl`。
- `query` 直接给作品 id 或作品链接也行（`artworkIdFromInput()` 会认出来），不再抓页面。
- **超 5MB 的原图**（4K 很常见，本期就有一张 5.34MB）会被 `image.maxBytes` 拦掉，此时改用同一项的 `thumbUrl`。

### 21.3 年龄分级

`socialV2.image.rating`（控制台「图片 / 表情来源（含搜图分级）→ 图片年龄分级」）：

| 档位 | 含义 |
| --- | --- |
| `safe`（默认） | 只返回全年龄；命中擦边词的滤掉 |
| `mild` | 允许擦边词 |

**词表本身可配**：`socialV2.image.ratingWords`，就在同一个弹窗里（三个「每行一个」的文本框）。语义是"**没配用默认，配了以你为准**"（显式留空 = 这个词表为空）：

| 键 | 作用 | 能不能删 |
| --- | --- | --- |
| `mild` | 判为擦边、`safe` 档会滤掉的词 | 能增能删（留空 = 不按词过滤擦边） |
| `tolerated` | 明确划为全年龄的词，**优先于 `mild`**（两张表都写了按全年龄算） | 能增能删（放宽记录就写这儿） |
| `explicitExtra` | 标签级的限制级词 | **只能加，不能减**（写进 `mild`/`tolerated` 也拦） |

**限制级（explicit）的实际判定**（2026-09-24 定稿）：内置标签表 `EXPLICIT_TAGS` **和标题兜底 `EXPLICIT_TITLE_RE` 都被有意清空了**，所以默认配置下**没有任何内容会被自动判为 explicit**——explicit 的唯一来源是管理员配的 `explicitExtra`（标签级，写进 `mild`/`tolerated` 也删不掉）。explicit 项在任何档位都不返回，`rating` 也放不开。配置与测试都以这个策略为准（`scripts/test-pixiv-search.mjs` 里有对应断言）。想恢复标题兜底见 21.11。

归一化在 `normalizeWordList()`：trim + 转小写 + 去重 + 单条限长 40 + 每个词表最多 300 条（防止有人把整本字典塞进 config）。控制台保存走 `POST /api/socialV2/config`，`merged.image.ratingWords` 会过一遍 `normalizeRatingWords()`，**非数组的键沿用旧值**，所以漏传某个键不会把词表清空。

判定依据是图源给的标签/标题（bobopic 的 alt），属于启发式：**宁可多滤**。所以 `safe` 档会误杀一部分正常图，代价由 `tolerated` 表来修；日榜项没有标签，按来源视为全年龄（综合榜和 R-18 榜是分开的）。

**2026-09 放宽过一次**（按实际误杀）：12 个"构图/场景/玩梗"标签从 `mild` 挪到了 `tolerated` —— `水泳` `お風呂` `風呂` `寝` `趴` `俯视` `lsp` `福利` `素足` `裸足` `紧身` `むね`。它们现在算 `safe`，两档都能返回。这两个表现在**都是配置项**，控制台里能看见谁被放走了，而不是某次改动里悄悄消失。

已知取舍：标签是**整标签匹配**，所以组合标签会漏（例如 `水着ワイシャツ` 不等于 `水着`，判为 `safe`）。要收紧的话得给少数强词加词干匹配，代价是误杀回升——目前选择保留宽松。

返回体里会带 `rating` 和 `notes`（例如"年龄分级=safe，滤掉 3 张擦边图"），bot 知道自己被滤了什么，不用猜。

### 21.7 排查记录：「来点永雏塔菲色图」为什么失败

现象：私聊里发「来点永雏塔菲色图」，bot 回「点名的也没有，换个人问吧」+「要图就要正经的，别老往那个方向拐」，**一次搜图都没调用**。

证据来自会话 transcript（`~/.dsh/sessions/--home-wx-qq-bridge-state-agents--/session-*/session.v3.jsonl.zstd`；注意这是**多帧 zstd**，`zstd -dc` 能全解，Node 的 `zstdDecompressSync` 只吃第一帧，会得到 213 字节的假象）。抽出来的两个原因：

1. **模型自己把「色图」判成露骨请求就拒了**，不是预设没生效 —— 同一份 transcript 的 `system/message`（turn 41）里确实带着 21b。原来的措辞是"这里的色图通常只是玩笑"，但模型读到「色图」两字仍先触发内容政策。改法：21b 现在直接规定**动作**（搜图 → 发图）和**禁止话术**（不许出现"色图没有 / 我不能给 / 要图就要正经的"），并写明"话题里出现『色图』两个字不改变你的动作"。
2. **就算它去搜 pixiv 也拿不到东西**：「永雏塔菲」在 bobopic 上当时只解析出 1 条无关结果，`塔菲` / `Taffy` 干脆没这个标签；而 B 站有 4 张相关图。所以新增 `source=auto`：先试 pixiv，**少于 3 张就自动补 B 站**（按 url 去重，notes 写明"pixiv 只有 N 张，已补上 B 站结果"）；显式 `source=pixiv` 失败时**不**偷偷换源，照实报错。
   - ⚠️ **2026-09-24 更正**：那句「只有 1 条」是**解析器过时**造成的假象，不是 pixiv 没图。bobopic 把标签页模板从 `…图片 | 2K分辨率 WxH` 换成了 `…图片|尺寸WxH`，`parseAlt` 只认旧的，于是整页只留下唯一还用旧模板的那条（`脚底/女孩`）。修好后同一页解析出 **13 条**塔菲作品（详见 21.10）。

沙盒验证（新建一个挂 `qq-chat-v2` 的会话，按真实唤醒格式喂同一句话；脚本 `scripts/test-imagereq-sandbox.mjs`，**它会真的往目标会话发消息**）：

| 版本 | 行为 |
| --- | --- |
| 改 21b 前 | 搜了 B 站，然后回「塔菲的图就这一张，爱要不要」+「色图没有，问一百遍也没有」 |
| 改 21b 后 | 搜了 pixiv + B 站，发「喏，塔菲」+ 一张塔菲图，没有说教 |

### 21.8 沙盒通过、QQ 里还是老样子：preset 只在建会话时读一次

改完 21b、沙盒验证通过之后，QQ 私聊里再发「来点永雏塔菲色图」**仍然一次搜图都没有**（回「点名的也没有，换个人问吧」）。原因是上一个盲区：

- **DSH 的 agent preset 是「会话创建时读一次、之后永久锁定」的**（`dsh-agent-presets` 的 `swap()` 会以 `agent-preset/locked` 拒绝给已开过回合的会话换 preset）。沙盒每次新建会话，所以读到的是新 21b；QQ 里那个会话建于 2026-09-21，`system/message` 里至今还是**旧版 21b**（旧版写的是「被要求发更露骨的内容时按人设一句带过」），模型据此继续拒绝。
- 判定证据：同一份 transcript 里，QQ 会话最后一次 `system/message`（23:21）是旧 21b，而 preset 文件 23:26 才更新；之后 23:46 / 23:48 / 23:49 的回合都没有再生成 `system/message`——DSH 复用了建会话时缓存的那份提示词。
- 沙盒跑「来点色图」（不带角色）：模型的第一个动作就是 `qq_search_images(source=pixiv, mode=daily)`，即直接查 pixiv 日榜——说明新 21b 的「第一个动作就是搜图」+「没给主题就取日榜」是有效的。

修法（两条，互补）：

1. **桥接侧每轮注入「要图请求」契约**（`src/bridge.js` 的 `withSlangContext`）：preset 管不到的已挂载旧会话，由这条每轮都到的提示兜住——「第一个动作就是 `qq_search_images`」「不许出现『色图没有 / 我不能给 / 换个人问』」「`rating` 就是管理员的结论，safe/mild 都该直接发，不要自己审查」。改完**重启桥接**即生效，不需要动 DSH。
2. **预设组成戳 + 会话自动重建**（`src/preset-stamp.js` + `bridge.js` 的 `sessionPresetStaleness`）：给每个会话记下建会话时 preset 的组成戳（`agent.cordis.yml` + `preset.yml` 的 sha1 前 16 位）；复用会话前比对，对不上（或老会话没记录）就退役旧会话、按新预设重建。于是「改了预设没生效」不再需要人工 `/reset`，也不必为了改预设重启 DSH。`socialV2.presetRefresh: false` 可关掉（代价是保留旧上下文、继续跑旧 preset）。

代价说清楚：自动重建会**丢掉那个会话的 DSH 上下文**（QQ 聊天记录还在，但 AI 记不住细节），日志与 `state/qq-activity.log` 会写一行 `preset ... 已刷新（...），旧会话退役重建`。这是「预设改动必须生效」与「保留上下文」之间唯一的选择——DSH 不支持给已开始的会话热换 preset。

验证：`node scripts/test-preset-refresh.mjs`（29 项，组成戳纯函数 + 接线 + 提示词存在性）、`node scripts/test-audit-bridge.mjs`（16 项，含「戳变了会退役重建」「刷新时令牌/bootstrap 保留」「`presetRefresh:false` 故意保留旧会话」）。

### 21.9 重启桥接后的第二次失败：重建把唤醒提示里的令牌作废了

重启桥接后，「来点永雏塔菲色图」确实触发了自动重建（日志：`preset qq-chat-v2 已刷新（会话建立于记录组成戳之前）：退役旧会话 …，按新预设重建`），但**那一整个回合所有工具都返回「agent token 无效」**，最后 AI 只在控制台留了一段「本轮无法执行任何动作」。两个原因都是这次改造自己带出来的：

1. **唤醒提示是先组好词、再 `ensureSession` 的**：`scheduleWakeV2` 先 `buildWakePromptV2()`（里面写死了当时的【会话令牌】），随后 `deliverPrompt → ensureSession` 才做陈旧判定。而 `retireSession()` 会**轮换 `st.agentToken`**（原本是为了撤销旧会话的调用权限）。于是刚发出去的提示词带着一个已被轮换掉的旧令牌，新会话这一回合读消息/搜图/发送/收尾全部被拒。修法：新增 `retireSession(key, { keepIdentity: true })`，preset 刷新时原样保留令牌与 `bootstrapSent`（同一个会话、同一个回合，没有撤销令牌的理由）；只有真正的权限/模式变化与 `/reset` 才轮换。
2. **老会话的 `bootstrapSent` 被清成了 false**，下一条消息会走「引导唤醒」而不是正常唤醒（有人等回话时 AI 却先去重新设唤醒配置）。修法：`takeBootstrapV2()`——只有「没有历史、也没被唤醒过」的新会话才引导；已有历史的会话顺手把标记修回来。这也顺带修复了已经被清掉的存量状态。

还有一个**独立的环境问题**（不是代码 bug）：`qq_search_images` 的 `source` 枚举里 `auto` 是后加的，而 DSH 侧那个 MCP 进程还是旧版本，所以模型传 `source=auto` 会吃到 `MCP error -32602: Invalid option: expected one of "bilibili"|"pixiv"|"all"`。**改 MCP 自己的 schema 只有重启 DSH 才会生效**（见 21.5）。所以人物引导改成「**每次显式写 `source`**：日系/色图 → `pixiv`，中文主播/梗图 → `bilibili`，两边都搜 → `all`」，这三个老 schema 都认；想用 `source=auto` 再重启 DSH。

### 21.10 「pixiv 上没有塔菲」是假的：bobopic 换了标签页模板

令牌修好、重启桥接之后，AI 的动作已经是 `qq_search_images(source=pixiv, query=永雏塔菲)`，但 pixiv 只回了 1 条（`脚底/女孩`、无标题），它判断不相干，转去 B 站发了两张评论图。用户指出「pixiv 上是有的」——**用户是对的**：

```bash
curl -s "https://bobopic.com/tag/%E6%B0%B8%E9%9B%8F%E5%A1%94%E8%8F%B2/" | grep -o 'href="/[0-9]*\.html"' | sort -u | wc -l   # → 13
```

页面里明明有 13 个作品（`永雏塔菲,大腿,脚底,脚指`、`永雏塔菲,黑丝袜,黑丝,女孩` …），`parseBobopicImages` 只提出 1 条。原因：**bobopic 把标签页的 alt 模板换了**——

| 模板 | alt 示例 |
| --- | --- |
| 旧（初音未来等页仍是） | `初音未来图片 - メイドさん \| 高清分辨率 960x1280` |
| 新（塔菲页整页都是） | `永雏塔菲,大腿,脚底,脚指图片\|尺寸1863x2795` |

`parseAlt` 的正则要求 `\| …分辨率 WxH`，新模板的 `|尺寸WxH` 直接不匹配 → 整页只剩唯一还用旧模板的那条（就是那张 `脚底/女孩`，纯属巧合），看起来就像「pixiv 没有塔菲」。

修法（`src/pixiv-search.js`）：正则改成 `图片` 之后「可选标题 + `|` + 任意尺寸描述」，尺寸从 `|` 之后的文本里取第一处 `WxH`（`尺寸1863x2795` / `2K分辨率 2676x3554` 都吃）。分界线仍用「`图片` 后面必须跟 `|`」，所以相关文章缩略图（`[pixiv]…共108张图片`，没有 `|`）照旧被跳过。测试里加了新模板夹具（含「新模板标签/尺寸解析」「仍走年龄分级」）。

复验（直连 bobopic，`rating=mild`）：`永雏塔菲` → `total 13 / kept 13 / 返回 8`，其中 `大腿`、`黑丝袜,黑丝` 两张判为 mild，其余 safe。

教训：**解析第三方页面时，「只有 N 条」要先怀疑自己的正则，而不是断定对方没有**。另外解析逻辑是桥接进程内加载的，改完要**重启桥接**才生效（这也是本轮连续三次重启的原因）。

### 21.11 把标题兜底也清空（EXPLICIT_TITLE_RE = ''）

2026-09-24：管理员要求把 `EXPLICIT_TITLE_RE` 也改空，做法与 `EXPLICIT_TAGS` 一致——

```js
// src/image-rating.js
export const EXPLICIT_TITLE_RE = '';   // 原来是 /(r-?18|18禁|…|露出|痴女)/i

// classifyImageItem() 里必须带真值判断：
if (EXPLICIT_TITLE_RE && EXPLICIT_TITLE_RE.test(String(title))) return { rating: 'explicit', … };
```

注意两点，否则会踩坑：

1. **不能写成空正则**。`new RegExp('')` 会匹配一切，等于把所有图都判 explicit；用空字符串（假值）+ 真值判断才表示「不启用」。原来这个常量没有 `export`，现在导出了，测试里可以直接断言它是空的。
2. **清空后 explicit 只会来自 `explicitExtra`**，而 `explicitExtra` 是**标签级**匹配、不匹配标题。所以想拦某个标题词，得靠图源把该词放进标签，或者另外加机制；默认配置下 `filterByRating` 的 `dropped.explicit` 恒为 0。

想恢复标题兜底：把上面注释里的历史正则填回常量即可（`src/image-rating.js` 的注释里留了一份）。这次改动同时更新了：`scripts/test-pixiv-search.mjs`（新增「标题兜底为空」「露骨标题按标签判 mild」等断言）、控制台提示文案、`src/bridge.js` 的注释。

### 21.12 「原图发送失败：请求超时：pixiv.re」

现象：`qq_send_image({"image":"https://pixiv.re/91401787.png"})` 返回
`发送图片失败：请求超时：pixiv.re`。（`safe-fetch` 的单次请求总时限是 `REQUEST_TIMEOUT_MS = 20000`。）

实测原因：**pixiv.re 不是慢一点，是常态性地慢**——它要现去 pixiv 拉原图再回给客户端：

| 源 | 结果 |
| --- | --- |
| `pixiv.re/<id>.png` | 1.19MB / **23.3s**（20s 超时必然失败；连续抓更容易吃 522） |
| `i.pixiv.re/<id>.png` | 该 id 直接 404 |
| `pixiv.cat/<id>.png` | 连不上（超时） |
| `img.pixivdaily.com/small/<id>.jpg` | 740×740、51KB、~2s（稳，但不是原图） |
| **bobopic「查看原图」通道** | **原分辨率、0.3~2s** |

最后一条是这次的关键：bobopic 详情页上那个「查看原图」按钮不是摆设，它的链路是

```
GET https://go.bobopic.com/<id>          → 302 /go.php?url=/tu/<id>.jpg
GET …go.php…                             → HTML：<img id="main-img" src="<sogou 代理的 weibo 图床原图>">
GET <sogou 地址>                          → 原图 JPEG
```

实测（本机，`safe-fetch` 走一遍）：`91401787` 1080×1080/819KB/0.5s、`149947902` 2000×2500/1.0MB/0.23s、`96174042` 5120×2880 也原样给。所以它比 pixiv.re 又快又是原图。

**修法**（`src/bridge.js` 的 `resolveImageBuffer`）：识别到 `pixiv.re` / `i.pixiv.re` 直链就走三段回退——

1. `fetchBobopicPixivOriginal(id)`：走上面的 bobopic 原图通道（原分辨率、最快）；
2. 失败 → 直接用传入的 pixiv.re，但把单次超时放宽到 **45s**（`safeFetchBuffer(..., { timeoutMs: 45000 })`，`safe-fetch` 新增按调用传 `timeoutMs`）；
3. 再失败 → `pixivThumbUrl(id)`（`img.pixivdaily.com/small/<id>.jpg`，740px）；
4. 全失败 → 报错里列出三段各自失败的原因，而不是只甩一句「请求超时」。

已知边界：**原图超过 `socialV2.image.maxBytes`（默认 5MB）时不会发原图**——例如 `115570927` 的原图 6.18MB，会走到第 2 步再被体积上限拦下，最后发 740px 缩略图。要原图就调大 `maxBytes`（控制台「单图体积上限」）。另外 `img01.sogoucdn.com` 这条只用于桥接内部回退，**没有加进 `refererAllow`**（那是个带 `?url=` 参数的通用代理，放给 AI 用会变成任意图床代理）。

验证：`test-audit-bridge.mjs` 新增 4 个离线用例（桩掉 `safeFetch`/`safeFetchBuffer`，验证三段顺序、45s 超时参数、缩略图兜底、以及「全失败时把试过什么都报出来」）；`test-pixiv-search.mjs` 覆盖 `pixivProxyIdFromUrl` / `pixivThumbUrl` 的边界（带 query、无扩展名、伪装域、pixiv 作品页不触发）。

### 21.13 真实 pixiv：代理 + 登录 cookie + r18 档

bobopic 镜像的标签页只有个位数作品、且**完全不含 R-18**（21.10）。2026-09-24 起本机有了 Clash 代理（`127.0.0.1:7897`），于是直接打 pixiv 官方接口：

| 能力 | 接口 | 是否需要登录 |
| --- | --- | --- |
| 关键词搜索 | `https://www.pixiv.net/ajax/search/artworks/<w>?word=<w>&mode=safe\|all\|r18&p=1&lang=zh` | `safe`/`all` 不用；**`r18` 必须登录** |
| 作品详情（取原图地址） | `https://www.pixiv.net/ajax/illust/<id>?lang=zh` | 不用（R-18 作品可能要） |
| 原图字节 | `https://i.pximg.net/...`（详情里的 `urls.original`） | 不用，但**必须带 `Referer: https://www.pixiv.net/`**（否则 403） |

实测：未登录时 `mode=r18` 与 `mode=all` 返回**完全相同**（60/60 全是 `xRestrict=0`，换 `中出`/`巨乳` 也一样）——pixiv 对未登录会话直接隐藏 R-18，所以「搜 R-18」这件事只有登录 cookie 能解。搜索质量差距很大：`永雏塔菲` 在 pixiv 搜索 `total=322`（bobopic 只有 13）；原图 `91401787` 走 i.pximg.net **1.19MB / 3.5s**（pixiv.re 是 23s）。

接线：

- `src/safe-fetch.js`：新增 `options.proxy`（HTTP 代理，`CONNECT` 隧道 + TLS，仍然校验证书）与 `options.timeoutMs`；`sanitizeImageHeaders` 放行 `cookie`（值来自本机 config.json，只在第一跳发送）。代理只对调用方点名的域名生效——桥接只对 pixiv 系域名开代理，bobopic / B 站继续直连。仍然是 `http://` 代理才收，`socks5://` 明确报错而不是悄悄直连。
- `src/pixiv-search.js`：`searchPixivWeb()`（搜索，`xRestrict` 0→safe、1→r18、2→explicit）、`pixivIllustOriginal()`（详情→原图直链）、`isPixivHost()`。
- `src/image-rating.js`：档位从两档扩到**三档** `safe ⊂ mild ⊂ r18`（`r18` 只由真实 pixiv 给出）；`explicit` 仍然任何档位都不放行。
- `src/bridge.js`：`socialV2.image.pixiv = { enabled, proxy, cookie }`；搜索时若配了代理就走真实 pixiv（`rating=r18` 时请求 `mode=r18`）、结果按 id 补原图直链（并发 4，失败退 `pixiv.re/<id>.png`）；抓图时 pixiv 系域名自动带 `Referer: https://www.pixiv.net/` 并走代理。`i.pximg.net` 进默认白名单。
- 控制台「图片 / 表情来源（含搜图分级）」：图片年龄分级多了 `r18` 档，另加「真实 pixiv（走代理）/ pixiv 代理地址 / pixiv 登录 Cookie」三个字段（cookie 是密码框）。

边界：cookie 是账号登录凭据，只存本机 `config.json`（已 gitignore）；pixiv 未登录时选 `r18` 档也不会报错，只是搜出来仍是全年龄（`notes` 里会写明图源与是否带登录）。代理挂了就回退 bobopic 镜像（`source=auto` 时）。

#### 21.13.1 两个实测踩到的坑

1. **cookie 只填值等于没登录**。管理员从浏览器里复制来的通常只是 `PHPSESSID` 的**值**（形如 `26362806_0n1L…`），直接当 `Cookie:` 头发出去是非法头（没有 `name=value`），pixiv 按未登录处理——表现就是「配了 cookie 但 `mode=r18` 还是全年龄」，完全不报错。修法：`normalizePixivCookie()` 自动补 `PHPSESSID=`，也接受整行 `Cookie: a=b; c=d`。
2. **登录后应该用 `mode=all` 而不是 `mode=r18`**。实测（带 cookie 且账号已开 R-18）：

   | mode | 单页分布（xRestrict） |
   | --- | --- |
   | `safe` | 60 × 0 |
   | `r18` | 47 × 1 + 13 × 2 |
   | `all` | 32 × 0 + 20 × 1 + 8 × 2 |

   `all` 是「全年龄 + R-18 混排」，交给 rating 档位筛即可（r18 档留 0/1、丢 2；mild/safe 档丢掉 1、2）。桥接因此固定用 `mode=all`。验证（`rating=r18`，真实 cookie）：`total=648 / kept=52 / returned=8`，返回项里 `{0:3, 1:5}`，R-18G 全部落在 `dropped.explicit`。

### 21.14 「重启桥接」按钮把手动启动的实例按死

现象：控制台点「重启桥接」→ 进程真的退出了，但**再也不会回来**。

原因：那个接口只做 `releaseLock(); process.exit(0)`，默认「有守护窗口（`start.bat` 的循环）会 5 秒后拉起」。Windows 上用 `start.bat` 启动确实如此；但在 Linux 上直接 `node src/bridge.js`（或任何没有守护的场景）按一下就永久下线。

修法（`src/bridge.js` 的 `/api/restart`）：

- `start.bat` 启动时设 `QQ_BRIDGE_GUARDED=1`（守护模式）→ 保持老行为：只退出，让守护窗口拉起；
- 没有这个变量（手动启动）→ 桥接自己 `spawn` 一个 **detached + unref** 的新进程（Linux 用 `sh -c 'sleep 1; exec node src/bridge.js'`，Windows 用 `cmd /c 'timeout /t 1 & node …'`；`stdio: 'inherit'` 所以日志还留在原终端），**先释放单实例锁再退出**。等 1 秒是为了让 3100 端口与 `state/bridge.lock` 释放，避免新进程撞锁/撞端口。
- 回执文案按实际走的路返回，不再笼统说「5 秒后恢复」。

测试：`node scripts/test-bridge-restart.mjs`（12 项，钉住两条路径、detached/unref、1s 延迟、释放锁顺序、start.bat 的守护变量）。

补充（Linux / macOS）：`start.bat` 只能在 Windows 用，所以补了语义一致的 shell 脚本——
`start.sh`（守护循环，设 `QQ_BRIDGE_GUARDED=1`，退出码 2 直接收工，Ctrl+C 不会又把桥接拉起来）、
`stop.sh`（**先停守护再停桥接**，按 `state/bridge-guard.pid` / `state/bridge.lock` 精确杀，
最后按 `node .*src/bridge\.js` 兜底并清锁）、`restart.sh`（先 `./stop.sh`，再 `nohup bash ./start.sh`
后台拉守护；`--fg` 前台）、`status.sh`（守护/桥接 PID、锁、控制台端口、最近日志）。
也有 npm 别名：`npm run start:guard` / `npm run restart` / `npm run stop` / `npm run status`。
断言在 `scripts/test-bridge-restart.mjs` 里（存在性、可执行位、`bash -n`、守护变量、停的顺序、清锁）。

### 21.15 两个线上问题：i.pximg 被白名单挡住 + 重复发图

**① 「pixiv 原图直链被 referer 白名单挡着，只能走 pixiv.re」**

现象：AI 手里已经是 `i.pximg.net` 直链（真实 pixiv 源给的），调 `qq_send_image` 却报
`图片站点不在 refererAllow 白名单内：i.pximg.net`，只好退回慢得多的 `pixiv.re`。

原因：`DEFAULT_REFERER_ALLOW` 里加了 `i.pximg.net`，但 **config.json 里有一份显式 `refererAllow`**（早先控制台保存过），`normalizeImageLimits()` 的语义是「配了就用你配的」，于是默认值被整份覆盖——网站在名单里就是没加。

修法两层：
- 把 `https://i.pximg.net` 补进 config.json 的 `refererAllow`（存量配置要手动补）；
- 代码层面兜底：`socialV2.image.pixiv.enabled = true` 时，**pixiv 系域名（pixiv.net / pximg.net / pixiv.re）始终放行**。它们是桥接自己产出的直链，不该被一份过期白名单挡住（`resolveImageBuffer` 里的 `pixivTrusted`）。

**② 图片重复发送**

同一个作品会在不同回合被反复发出来（搜图每次给的 top 结果相同；模型换了个镜像地址也照样是同一张）。

修法：按**作品身份**去重，而不只是比 URL 字符串——
- `pixivArtworkIdFromAnyUrl()` 从任意 pixiv 系地址认作品 id（`pixiv.re/<id>.png`、`i.pximg.net/.../<id>_p0_square1200.jpg`、`img.pixivdaily.com/small/<id>.jpg-220`、`pixiv.net/artworks/<id>`），认得出就 `pixiv:<id>`，认不出退化成「去掉 query 的 URL」，本地图库用文件名；
- **搜图结果**里自动滤掉最近发过的（`notes` 写「已跳过 N 张…」，全被滤掉时提示换关键词）；
- **`qq_send_image`** 命中最近发过的身份会直接拒绝（错误信息告诉 AI 换一张）；`qq_send_sticker` 不受影响（表情包本来就该重复用）；
- 窗口 `socialV2.image.repeatGuardMs`，默认 6 小时，`0` = 关闭；控制台「防重复发图窗口（分钟）」。

测试：`test-pixiv-search.mjs` 加了身份识别用例（不同镜像/尺寸必须算同一张）；`test-audit-bridge.mjs` 加了「同一张换镜像仍被拒 / 换一张能发 / 窗口置 0 关闭」三个用例。

### 21.16 「小草神被草的」到底被谁过滤了

AI 的回答是「限制级那块是滤掉的，搜也搜不出来，怎么调都到不了这一步」。分开验，实际是**三层，只有一层是我们拦的**：

| 层 | 现象 | 实测 |
| --- | --- | --- |
| ① pixiv 搜索本身 | 整句话不是一个标签 → 0 条 | `小草神被草的` → `total=0`（所以「搜不出来」是对的） |
| ② 我们拦 R-18G | `xRestrict=2` → `explicit` → 任何档位不放行 | `小草神` → `total=104 / kept=58 / dropped.explicit=2` |
| ③ pixiv 账号门禁 | R-18G 需另开「R-18G の閲覧」；非公开/不可搜索的作品不出现 | —— |

代码位置：`pixiv-search.js` 的 `pixivWebItem()` 把 `xRestrict>=2` 标成 `explicit`，`image-rating.js` 的 `imageRatingAllowed()` 里 `if (itemRating === 'explicit') return false;` 硬拦；回执里就是那句「滤掉 N 张限制级图（任何分级都不返回）」。

**但「被草的」这类内容并不是到不了**——只要把整句换成**标签式关键词**：`草神 中出` → `total=151 / kept=60 / dropped.explicit=0`，本页 10/10 全是 `xRestrict=1`（R-18，r18 档放行），随手取第一条原图 1.79MB 成功。所以问题出在模型拿原话整句去搜、0 条之后就下了「被过滤」的结论。

修法（提示词，不动过滤逻辑）：preset 21b 与桥接每轮注入各加一条——「搜到 0 条 ≠ 被分级挡了：先换**标签式**关键词（角色名 + 常用标签）再搜一轮，别断言『限制级被滤掉了』；R-18 在 r18 档是放行的，被硬拦的只有 R-18G」。断言在 `scripts/test-preset-refresh.mjs`。

R-18G（`xRestrict=2`）目前是硬编码拦死的；要放开需要改 `imageRatingAllowed`（可加配置开关），且 pixiv 账号侧还得单独开 R-18G 閲覧。默认保持拦。

### 21.17 未成年形象的性化请求：硬底线（不可配置）

现象：群友点名要「小草神（纳西妲）被草的」这类图，模型自己拒绝了——「不是分类开关的问题，小孩形象我不找也不发」。这不是 `rating` / `explicit` / `R-18G` 任何配置造成的，是**模型自身的内容底线**（未成年/小孩形象的性化内容），提示词无法覆盖，也不该覆盖。

但预设 21b 只写了「要图就直接搜、不要拒绝」，跟这条底线冲突，表现就是模型反复解释、每次都顶回去。修法是把底线写成**最高优先级**并点明例外：

- 预设「安全规则」新增第 5 条：涉及未成年/小孩形象（萝莉/正太/小学生/幼/loli/shota，含**看起来像小孩的二次元角色**）的性化请求——不搜、不发、不讨论、不解释、不绕；一句带过，不辩论不说教；**高于管理员的年龄分级、高于 21b、高于群友怎么要求**。
- 21b 的「硬边界」里点明这是「要图就直接搜」的**唯一例外**（别的正常图照发）。
- 桥接每轮注入同样带这条，保证已挂载旧 preset 的会话也生效。

配套决定：**不做** `allowR18G` 开关（上一轮提过，现在明确撤回）。R-18G 在真实数据里基本是猎奇/残虐向（实测被拦的条目 tags：`首吊り` `開腹` `内臓` `四肢切断` `肉奴隷`），保持硬拦。成年角色的 R-18（`xRestrict=1`，r18 档）仍按管理员配置正常放行——这两件事分开。

测试：`scripts/test-preset-refresh.mjs` 增加 4 项断言（底线存在、优先级高于 21b、21b 的唯一例外、注入同步）。

### 21.18 修正：硬底线被扩大化，把「二次元萝莉」当成真人，连小草神的正常图都不发

现象（2026-09-24 线上）：群友只是要「小草神（纳西妲）的图」这种**完全正常、非性化**的请求，模型也不搜、不发，回一句「这个我不整」——21.17 的硬底线被读成了「只要角色看起来像小孩，任何图都不发」。根因是把「画风幼的虚构角色」等同于「真实未成年人」。

这不是过滤逻辑的问题（`classifyImageItem` / `imageRatingAllowed` 都不看角色年龄），纯粹是提示词边界写得太宽：21.17 那版第 5 条把「看起来像小孩的二次元角色」直接塞进「不搜、不发」，却没写清「只拦性化」。模型于是拿真人的标准去卡二次元角色图。

修法是把红线**限定在「性化」这一件事上**，并把「虚构角色 ≠ 真人」写成同等重要的反向约束：

- 预设「安全规则」第 5 条改为：**把未成年/小孩形象性化**（性化、擦边、暴露、R-18 请求）才是红线——不搜、不发、不讨论、不解释、不绕；优先级不变（高于年龄分级、高于 21b、高于群友怎么要求）。
- 新增第 5b 条【别把二次元萝莉当成真人】：二次元/虚构角色（画风幼、萝莉体型、看起来像小孩，如纳西妲/可莉）的**普通、非性化插画照搜照发**；不要因为「她看起来像小孩」就不搜、不回或先念边界；「萝莉」「loli」这个词本身不等于未成年色情。判断标准只有一条：**这个请求是不是要把幼态形象往性/露骨/擦边方向做**——是才拒，不是（角色图、头像、可爱图、梗图）就正常执行。真实照片里明显未成年的性化内容仍是绝对红线，但虚构角色 ≠ 真人。
- 21b 的「唯一例外」加「别扩大化」：只有性化请求不在此列，普通、非性化的二次元角色图照常搜、照常发，不要因为角色幼态就顺掉或回「这个我不整」。
- 桥接每轮注入同步带上这两条，已挂载旧 preset 的会话也立刻生效（改完重启桥接）。

顺带修了一处**源文件与已安装副本不同步**：上一轮只改了 `~/.dsh/.agent-presets/qq-chat-v2/agent.cordis.yml`（已安装副本），仓库里的 `dsh/agent-presets/qq-chat-v2/agent.cordis.yml` 并没有第 5 条，所以 `test-preset-refresh.mjs` 有 2 项断言一直红着、重装一次预设就会把修复覆盖掉。现在仓库文件是唯一真源，改完用 `cp`（或 `node scripts/setup-dsh.mjs`）同步到 DSH_HOME。

测试：`scripts/test-preset-refresh.mjs` 由 31/2 变为 **38 通过 0 失败**，新增 5 项断言（二次元萝莉≠真人、非性化幼态角色图照搜照发、虚构角色≠真实未成年人、21b 例外不扩大化、桥接注入同款区分）。
