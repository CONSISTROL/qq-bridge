## 补充（2026-10-18 16:12）：qq-mode-console 插件 failed to import

现象：tzd 上 DSH 日志出现 `qq-mode-console (qq-mode-console): failed to import`，
阿里云上则是 `[qq-mode-console] active (namespace=qq-mode)`。

根因：插件 `plugins/qq-mode-console/lib/index.js` 把 DSH 的 schemastery 路径**硬编码**成
```js
'/usr/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/schemastery/lib/index.cjs'
'/usr/local/lib/node_modules/@deepseek-ai/dsh/...'
```
它必须用 DSH 自己那份（3.18.4+ 才有 `.volatile()`），仓库依赖树里的 3.18.1 没有。
初次迁移时 DSH 装在 `/opt/node22/lib/node_modules/`，两个候选路径都不存在 → `loadZ()` 返回 null → 插件 import 失败。

修法（插件零改动）：按阿里云同样的标准前缀重装 DSH
```bash
export PATH=/opt/node22/bin:$PATH
npm i -g --prefix /usr @deepseek-ai/dsh@0.2.0-rc.2 --registry=https://registry.npmmirror.com
# 得到 /usr/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/schemastery = 3.18.5（有 volatile）
# /usr/local/bin/dsh 包装器改为指向 /usr/lib/node_modules/@deepseek-ai/dsh/lib/bin.js
systemctl restart dsh-web.service
```
验证：`grep qq-mode-console 最新 server-*.out.log` 应看到 `[qq-mode-console] active (namespace=qq-mode)`，
`state/qq-mode-plugin.log` 里有 `configure ok (namespace=qq-mode, auto=false)`。

## 补充（2026-10-18 16:35）：DSH 网页的 token 全自动化，管理员不再需要它

### 问题
`dsh web` 每次启动生成新的随机 launch token，鉴权 cookie 名字是 `dsh-auth-<token哈希>`。
所以 DSH 每重启一次，浏览器里的旧 cookie 就全部失效 —— 页面壳子能打开，但 `/api/*` 和
WebSocket 全 401，前端表现就是**永远「重新连接中」**。

### 做法：`dsh-token-proxy`（tzd 上的自愈代理）
文件：`/root/.dsh/guard/token-inject-proxy.mjs`
单元：`dsh-token-proxy.service`（enabled），监听 `10.8.0.2:3080` → 转发到 `127.0.0.1:3080`

每个请求它都做四件事：
1. 从**最新的** `guard/logs/server-*.out.log` 里读出当前 token（每次请求都读，重启后自动跟上）；
2. 用 `GET /?token=<token>` 换一次 `Set-Cookie`，缓存住；token 变了就重换；
3. 转发前**丢掉浏览器带来的所有 `dsh-auth-*`**，只注入代理自己那份；
4. 把 URL 里的 `?token=` 抹掉，避免 303 跳转。

WebSocket（`/api/remote.mux`）走 `upgrade` 分支，同样注入 cookie。
另有每 30 秒一次的后台刷新，DSH 重启后不用等第一个 401。

替换掉了原来的 `dsh-wg-proxy.socket`（纯转发，已 disable，文件保留）。

### 为什么放在 tzd 而不是阿里云
token 只存在于 tzd 的启动日志里。放 tzd 可以**读本地文件**；放阿里云就得跨机同步这个易变值，
反而更脆。对管理员来说没有区别：anihub 的 3080 卡片现在显示 **「DeepSeek Harness · HTTP 200」**，
点开即用，永远不用管 token。

### 验证（模拟全新浏览器，零 dsh-auth cookie）
| 请求 | 结果 |
| --- | --- |
| 页面 | 200 |
| `/api/remote.mux` WS 握手 | **101** |
| WS 握手 + 故意塞过期 `dsh-auth` cookie | **101**（被剥掉） |

### 注意
- DSH 重启的瞬间仍可能闪一下「重新连接中」（1~3 秒）：那一次响应还是旧的 401，
  但代理会立刻作废缓存，下一次请求/重连就恢复。不再需要人工干预。
- 万一 `dsh-token-proxy` 挂了：`systemctl restart dsh-token-proxy`，
  日志在 `/root/.dsh/guard/token-proxy.log`。

## 补充（2026-10-18 16:52）：页面「一直重新连接中」—— anihub 改写 JS 字面量导致的

### 现象
页面壳子能渲染、插件也加载了，但右下角一直「重新连接中」。nginx 日志里能看到：

```
GET /local-web/http/127.0.0.1:3080/local-web/http/127.0.0.1:3080/api/remote.mux 502
```

**前缀重复了两遍。**

### 根因（用无头 Chrome 抓到的实证）
1. anihub 的本地 Web 代理除了 HTML，还会**改写 JS 里的根路径字符串字面量**。经代理拿到的
   `plugins/??...dsh-api-gateway/client.js` 里：
   ```js
   直连 DSH:   const REMOTE_STREAM_MUX_PATH = "/api/remote.mux"
   经 anihub:  const REMOTE_STREAM_MUX_PATH = "/local-web/http/127.0.0.1:3080/api/remote.mux"
   ```
2. DSH 客户端算实时通道地址用的是：
   ```js
   new URL(REMOTE_STREAM_MUX_PATH.slice(1), __DSH_TRANSPORT__?.streamBaseUrl ?? document.baseURI)
   ```
   `slice(1)` 把开头那个 `/` 去掉 → 变成**相对路径** `local-web/http/.../api/remote.mux`，
   再拼到已经带前缀的 `document.baseURI` 上 → 前缀两遍 → anihub 侧 502。

### 修法（在 tzd 的 `dsh-token-proxy` 里，不动 anihub）
`dsh-token-proxy` 转发 HTML 时注入一段极小的传输垫片：

```js
if (!g.__DSH_TRANSPORT__) g.__DSH_TRANSPORT__ = { ownsHost: true };
g.__DSH_TRANSPORT__.streamBaseUrl = location.origin + '/';
```

`streamBaseUrl` 取纯 origin 后两种情况都正确：
- 被改写过的字面量（相对、已含前缀）→ `origin + 前缀 + /api/remote.mux` ✅
- 原始字面量 `/api/remote.mux` → `origin + /api/remote.mux`，再由页面垫片补一次前缀 ✅

### 验证（真实无头 Chrome，经完整 anihub 链路）
| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| WS 地址 | `.../3080/local-web/http/127.0.0.1:3080/api/remote.mux` | `.../3080/api/remote.mux`（单前缀） |
| WS 握手 | 502 | **101 Switching Protocols** |
| 页面「重新连接中」 | 是 | **否** |
| 侧边栏/会话/工作区 | 不显示 | 正常 |

### 排查方法（可复用）
tzd 上有桥接带的 puppeteer + Chrome（`/root/.cache/puppeteer`），可以直接跑无头浏览器：
设好 `anihub_local_web` cookie → 打开代理地址 → 用 CDP 的
`Network.webSocketCreated` / `Network.webSocketHandshakeResponseReceived` 看真实 WS 地址与握手结果，
并在页面里读 `document.baseURI` / `__DSH_TRANSPORT__`。比 curl 猜快得多。

### 已知无害残留
控制台仍有一条 `manifest.webmanifest 401`（PWA 清单没走鉴权）和一条 404，
不影响功能。

## 补充（2026-10-18 17:05）：补上 qq-bridge 控制台等三个端口的入口

### 现象
anihub 打开 3100 报 `PROXY_FAILED：无法连接 127.0.0.1:3100`。

### 原因
桥接搬到 tzd 后，3100（控制台）、5099（SnowLuma WebUI）、6081（snowluma noVNC）
都只在 **tzd 的 127.0.0.1** 上监听；而 anihub 的本地 Web 只允许**回环上游**。
阿里云侧那三个端口原本是桥接/容器直接占的，迁移后空了，我也漏了给它们建桥
（之前只建了 3080/6082/7865）。

### 修法（两端各三个 socket，共六个单元，均已 enabled）
| 端口 | tzd 侧（10.8.0.2:PORT → 127.0.0.1:PORT） | 阿里云侧（127.0.0.1:PORT → 10.8.0.2:PORT） |
| --- | --- | --- |
| 3100 桥接控制台 | `qq-console-wg.socket/.service` | `qq-console-proxy.socket/.service` |
| 5099 SnowLuma WebUI | `snowluma-webui-wg.socket/.service` | `snowluma-webui-proxy.socket/.service` |
| 6081 snowluma noVNC（扫码/登录用） | `snowluma-novnc-wg.socket/.service` | `snowluma-novnc-proxy.socket/.service` |

### 控制台令牌
桥接控制台的 token 是**持久化**的：`state/console-token`（48 位，随迁移一起过来），
只在 `config.consoleToken` 为空时生成一次并落盘，**不随重启变化**（这点和 DSH 不同）。
请求可带 `?token=`、`x-console-token` 头，或登录后下发的 HttpOnly cookie。
打开一次带 token 的地址后，页面会把它存进 `localStorage['consoleToken']`，之后裸地址即可。
